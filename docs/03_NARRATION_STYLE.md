# 03 旁白写作规范

这份规范管**听的东西**：旁白、提问者台词、屏幕字，以及配音的语气（第 12 节）。它是写书规范的"口语版"——同样要求说人话、讲为什么、数字带条件，但耳朵比眼睛更没耐心。

`tools/lint_script.py` 会机器检查其中一部分（禁用词、句长、数字必须挂事实、屏幕字长度）。机器查不出的，由 viewer 和 showrunner 把关。

## 1. 总原则

想象你在给一位聪明的同事边画图边讲。他随时会打断问"为什么""具体多少""代价呢"。旁白要提前回答这些问题。

1. **一个镜头一个意思。** 一个镜头（15–30 秒）只推进一个要点。讲不完就拆镜头。
2. **先结论，后原因。** 每个镜头的第一句就是要点。
3. **耳朵记不住长句。** 听的人不能回头重读。句子要短，主语要近。
4. **画面和旁白分工。** 画面负责"结构和数量"（谁在哪、有多少、先后顺序）；旁白负责"因果和取舍"（为什么、代价是什么）。不要用旁白念屏幕上已经写着的字。

## 2. 句子

- 目标长度 15–30 字；超过 42 字 lint 会警告，超过 60 字报错。
- 一句只有一个新概念。新术语后面紧跟一句白话。
- 少用书面连接词："因此""然而""此外"换成"所以""但是""另外"，或者干脆断句。
- 不用长定语。
  - ✗ 基于置信度估计的面向草稿 token 的动态长度验证机制
  - ✓ 先估计每个草稿 token 能不能被接受，再决定这一步验证几个。
- 主语明确："调度器把请求分给……"，不写"请求被进行分配"。
- 时长按配音后端的实测语速估算（`tools/voices.yaml` 的 `cps`）。Qwen 解说音色实测约 4.9 字/秒（EP99 4.57，试点 EP07 4.90），一个 20 秒的镜头大约 95 字；以 `pacing_report.py` 的实测值为准，偏差超过 10% 就校准。

## 3. 数字

- **每个数字都挂事实 ID**（镜头元数据 `facts:`），lint 会检查。
- **口播带条件，屏幕写全条件。** 旁白可以简短（"按 DeepSeek 自己的数据"），但屏幕上的数字卡必须有灰色条件行（谁、什么硬件、什么配置、什么负载）。
- **数字后面跟"所以呢"。** "每 token 890 字节"之后要有一句"一百万 token 的上下文，块状 KV 不到 1 GB"。
- **难念的数字用读音标注**：`{1,415,040|约一百四十一万}`、`{EP64|E P 六十四}`。原则：字幕写精确值，口播可以说约数，但约数不能改变含义。
- **不同条件的数字不在同一句里比较。** 要比就先把条件摆出来，并说明能不能比。

## 4. 证据措辞（与角标一致）

| 角标 | 口播这样说 | 不要这样说 |
| --- | --- | --- |
| A 代码证实 | "代码里……""在 `cache_engine.py` 里能看到……" | — |
| B 官方文档 | "DeepSeek 在部署问答里说……""按 README 的说法……" | 把官方宣称说成客观事实 |
| C 第三方实测 | "vLLM 团队在 GB200 上测到……" | "据测试""实测表明" |
| D 社区说法 | "有人认为……，但没有找到一手证据" | 当事实用 |
| E 推断/示意 | "从这两点可以推断……，不过文档没有直接说""这是一个示意的算法" | "显然""不难看出" |
| 不知道 | "公开资料没有说明" | 含糊带过 |

范围标签同理：讲"仅文档描述"的内容时，口播至少说一次"这部分代码没有开源"。

## 5. 术语

- 第一次出现：中文名 + 英文 + 一句白话（`01_SERIES_BIBLE.md` 第 7 节）。之后全系列用同一个叫法。
- 代码内部名字（ZOS、YOCO、CED、DSpark、Engram）第一次出现时说"这是代码/文档里的叫法"，并解释它指什么。
- 一个镜头里新术语不超过两个。
- 配音读不准的词：先查 `tools/lexicon.yaml`，没有就用 `{写法|读法}` 内联标注，并在报告里提醒 pipeline-engineer 加进 lexicon。

## 6. 提问者（Q）

- 一句话，问真实的疑问。好问题的来源：viewer 审读记录里的"读完的疑问"。
- 频率：大约每 3–5 个镜头一次。不密于每 3 个镜头一次，也不疏于每 6 个镜头一次；一集 20 个镜头约 4–6 个 Q。试点 EP07 只在冷开场有 1 个 Q，之后 13 分钟全是独白，节奏发闷——这是缺陷，不是"克制"。`lint_script.py` 和 `pacing_report.py` 会警告。
- 位置：放在观众刚产生疑问的地方——机制讲完、代价之前、aha 之前、数字刚出现时。好来源是 viewer 审读里的"读完的疑问"。
- 不要用提问者做无意义的捧哏（"哇，好厉害！"）。
- 好的 Q：
  - "只看最后 140 个位置，前面的信息不就丢了吗？"
  - "那为什么不直接用张量并行？"
  - "这和上一集说的'CPU 晚一步'冲突吗？"
- 坏的 Q：
  - "这是什么意思呢？"（太空）
  - "听起来很厉害，能详细说说吗？"（捧哏）

## 7. 类比

- 可以用，但要准，并且说清在哪里不成立。
- 一个概念最多一个类比。
- 优先用"具体的数字例子"代替类比。"一万个 token，后 20 层只算最后 140 个"比任何比喻都清楚。
- 禁止和技术无关的生活化凑趣（"就像餐厅服务员……"），除非它真的帮助理解，并经过 viewer 盲测。

## 8. 屏幕字

- 每行不超过 20 字（lint 警告），一个镜头不超过 4 行。
- 屏幕字是"要点和数字"，不是旁白的复写。
- 代码标识符用等宽字体，原样拼写。

## 9. 禁用与慎用

禁用（lint 报错）：

> 赋能、助力、全方位、多维度、深度融合、极致、颠覆、革命性、里程碑、底层逻辑、抓手、闭环、打通、生态位、降本增效、值得注意的是、不难看出、综上所述、众所周知、毋庸置疑、扮演着、起到了、具有重要意义、黑科技、炸裂、吊打、遥遥领先、不可思议、暴力、腰斩、震撼、彻底理解、彻底搞懂、彻底明白、一文读懂

慎用（用了就要紧跟具体内容）：显著、大幅、高效、优化、灵活、强大、先进、核心、关键、巧妙、优雅。

## 10. 正反例

### 例 1：介绍一个机制

✗
> DeepInfer 通过引入 DSpark 与基于置信度的调度验证机制，在投机解码场景下实现了验证算力的精细化动态分配，显著提升了系统吞吐。

问题：一句塞五个概念；"精细化""显著"是空话；没有数字；耳朵根本跟不上。

✓
> 草稿每次猜 5 个 token。可这 5 个并不一样靠谱，越往后越容易猜错。
> 全拿去验证，很多算力就花在了大概率被拒绝的 token 上。
> DSpark 先估计每个 token 能不能被接受，再决定这一步验证几个。

### 例 2：讲代价

✗
> 当然，这种方案也存在一定的局限性，需要在实际应用中权衡。

✓
> 代价是：CPU 看到的永远是上一步的结果。一个请求在第 N 步已经结束了，CPU 要到第 N+1 步才知道。

### 例 3：讲不确定的事

✗
> Engram 模块显然用于实现高效的记忆增强。

✓
> 代码里有一组叫 Engram 的模块。从输入看，它在用最近几个 token 查一张巨大的表。DeepSeek 的公开文档没有解释它的设计，这里只讲代码里看得到的部分。

### 例 4：冷开场

✗
> 大家好，欢迎来到 DeepInfer 系列的第七集。这一集我们要讲一个非常重要的技术。

✓
> 一个四十层的模型，处理一万个 token 的输入。后面二十层，只算了最后 140 个位置。
> 答案还是对的吗？大部分时候是。这一集讲它为什么敢这么做，以及"大部分时候"是什么意思。

## 11. 写完一个镜头后自问

1. 第一句是不是这个镜头的要点？
2. 删掉这个镜头，观众会损失什么？说不出来就删。
3. 有没有一个术语第一次出现却没解释？
4. 有没有一个数字没挂事实、没带条件？
5. 闭上眼只听旁白，能听懂吗？只看画面（静音），能看出结构吗？

## 12. 配音语气（instruction）

正式配音用 Qwen-Audio-3.1-TTS-Plus（选型理由见 `09_PRODUCTION_PIPELINE.md` 第 3.4.1 节）。它每次合成都接收一条自然语言 `instruction`，用来控制**怎么读**。这一节规定这条提示词怎么用。

### 12.1 音色分配（全系列固定）

| 角色 | 音色 | 默认语气（`voices.yaml` 中的 `n` / `q`） |
| --- | --- | --- |
| 讲解者（旁白） | `longanhuan_v3.1` | 沉稳、清晰、富有逻辑的科技讲解口吻 |
| 提问者（`Q：` 行） | `longanlingxin_v3.1` | 好奇、探究、求真的提问口吻 |

H2 之后音色锁定，全系列不换。要换必须先写进 `work/decisions.md`，并整季重配。

### 12.2 语气预设

镜头元数据里写 `tone: <预设名>`，只改变本镜头**旁白行**的语气；提问者永远用 `q`。不写就用 `n`。大部分镜头都不该写。

| 预设 | 用在哪里 | 提示词（`tools/voices.yaml`） |
| --- | --- | --- |
| `n`（默认） | 正文 | 沉稳、清晰、富有逻辑的科技讲解口吻 |
| `hook` | 冷开场 | 平静地抛出一个反直觉的事实，略带悬念，不夸张 |
| `card` | 片头卡、段落卡 | 简短平稳地报出标题，不拖音 |
| `cost` | 讲代价的镜头 | 坦诚克制地讲代价，不带褒贬，语速与正文一致 |
| `caveat` | 讲不确定、讲简化、讲"文档没说"的镜头 | 谨慎平实，像在说明限制条件，不含糊 |
| `recap` | 结尾"三句话" | 清楚有力地总结，句间自然停顿，语速与正文一致 |
| `q`（保留） | 提问者，自动使用 | 好奇、探究、求真的提问口吻 |

一集里写了 `tone` 的镜头通常不超过 5 个：冷开场、片头卡、代价段、三句话，外加一两个讲限制的镜头。

### 12.3 提示词写法规则

改动或新增预设时遵守：

1. **只管怎么读，不管读什么。** 写语气、节奏、情绪强度（"沉稳""稍慢""一句一顿"），不写内容、不写事实、不写"强调某个数字"。
2. **短。** 不超过 30 个字，一条只描述一种状态。
3. **克制。** 系列口吻是"懂行的工程师同事"（`01_SERIES_BIBLE.md` 第 5 节）。不用"激动""震惊""热情洋溢""播音腔""带货"之类的词；不模仿任何真实人物的声音或风格。
4. **不用语气修读音。** 读错的词进 `tools/lexicon.yaml` 或用 `{写法|读法}`；instruction 改不了读音，还会让整句语气漂移。
5. **不用语气凑时长。** 镜头太长就删句子，太短就补内容或加 `[pause:x]`；不要靠"读快一点"压时长。
6. **强调靠写法。** 想让一句话被听清，把它写短、单独成句、前面加 `[pause:0.6]`，而不是加一条"重读"提示。
7. **脚本里不写自由文本。** 只能引用预设名；`lint_script.py` 对未定义的预设报错。新预设由 pipeline-engineer 加进 `voices.yaml`，写明用途，并在 `decisions.md` 记录；改了提示词文字，用到它的分句都会重配。
8. **试听验收。** 新预设至少在 EP99 或试点集里合成 3 句给委托人听（H2）；模型听不了音频，不能自己判定"好听"。

### 12.4 语速

不同语气的实际语速不同。`parse_script.py` 的估算只按后端的平均语速算，所以带 `tone` 的镜头以配音后的 `timing.json` 为准。

- **任何预设的实测语速与正文相差不超过 20%。** `tools/pacing_report.py`（`make_episode.sh` 在配音后自动跑）逐镜列出字/秒，超出就警告。
- 试点 EP07 的教训：旧 `recap` 写了"语速稍慢，一句一顿"，实测 2.39 字/秒（正文 4.90，慢 51%），"三句话"从 42 秒拖到 68 秒；旧 `cost` 写了"语速稍慢"，慢 23%。模型对速度词反应很强，所以**提示词里不写速度词**（"稍慢""放慢""一句一顿"），节奏用 `[pause:x]` 和短句控制。
- "三句话"镜头不超过 45 秒：每句一条要点，不展开。
- 每个 aha 前留 `[pause:0.6]`–`[pause:1.0]`（04 第 5 节）。试点 EP07 只有冷开场有停顿，S06、S13 的揭晓都是连着念过去的。
