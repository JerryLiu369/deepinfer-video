# 06 事实协议

视频比书更容易"说错了也没人发现"：旁白一闪而过，观众无法回头查证。所以这个系列对事实的要求比书更严：**成片里每个技术断言都能追到账本里的一条记录，每条记录都能追到一手来源。**

## 1. 证据等级

| 等级 | 含义 | 证据要求 | 屏幕角标 |
| --- | --- | --- | --- |
| A 代码证实 | 在固定 commit 的源码里能看到 | `路径:行号` + `commit` + 原文摘录 | `A 代码证实`（绿） |
| B 官方文档 | DeepSeek 的 README、`doc/`、技术报告、官方知乎、官方 X、HF 模型卡与 `config.json`；vLLM/SGLang 官方文档与官方博客 | URL 或 `文档路径:行号` + 摘录 | `B 官方文档`（蓝） |
| C 第三方实测 | 有可复现方法的测试（附脚本或完整配置） | URL + 测试条件 | `C 第三方实测`（紫） |
| D 社区说法 | 媒体、博客、论坛、知乎回答、推文转述 | URL | `D 社区说法`（灰） |
| E 推断/示意 | 由 A/B/C 推出的判断，或为讲解构造的示意数字 | 推理过程写在 `caveat`，或计算脚本 `calc` | `E 推断/示意`（金） |

规则：

1. 每集的核心结论（"看完能说出"的三句话）至少要有 A 或 B 支撑。
2. A 与 B 冲突时以 A 为准，**两者都上屏**，并讲清差异（例如文档说"重算最后 128 个 token"，代码要求保留 ≥ 134 行、README 设 140）。
3. D 级只能以"有人认为……，没找到一手证据"出现，不能支撑任何结论。
4. E 级必须在旁白里听得出是推断（"可以推断""这是示意"）。
5. 性能数字必须写清：谁测的、什么硬件、什么配置、什么负载、和谁比。

## 2. 核验流程（fact-checker）

对每条准备入账的事实：

1. **找线索**：从大纲、研究笔记（`R01–R18`）、书稿里拿到说法。线索本身不是证据。
2. **回到一手来源**：
   - 代码类：在 `$DV_KB/sources/DeepInfer`（commit `9bd9cf2`）里打开文件，读到对应行。确认行号没变，摘录原文。
   - 文档类：打开 `doc/inference_deployment_qa.md`、README、HF 模型卡等原文，摘录原句。
   - 外部类：打开原始 URL。打不开就记 `unverifiable`，不要用二手转述代替。
3. **读上下文**：至少读断言前后 30 行，确认没有被条件分支、默认值、环境变量改变含义（例：`KEEP_TOKENS` 代码默认是 0，140 是 README 的推荐设置）。
4. **算一遍**：派生数字一律写成 `work/calc/` 脚本跑出来，不心算。
5. **写条目**：按 `05_FORMATS.md` 第 1 节格式。`verified_by` 写 `fact-checker@<日期>`（第二核验人写 `fact-checker-2@…`，对比任务写 `fact-diff@…`）；其他角色不能签，`lint_facts.py` 会报错。从 `examples/` 复制来的 `sample@…` 条目必须重新核验后改签。
   - 引用第三方实测时，每个数字单独写条件。例：vLLM PR 的 TTFT 降幅分 TP4 与 DEP4 两组、从 16K 输入起算；"精度在约 1.5 个标准误以内"出自 vLLM 博客、基于 GSM8K 与 GPQA，逐点数字只有 GSM8K——这三件事不能合成一句"vLLM 测得又快又不掉点"。`claim` 要精确到"能被证伪"的程度。
6. **找反例**：问自己"这句话在什么情况下不成立？"写进 `caveat`。

不可做：

- 用笔记里的行号直接入账而不打开源码确认。
- 把"代码里有这个函数"写成"生产在用这个功能"。
- 把"测试存在"写成"测试通过"（没有人跑过这些测试）。
- 用 grep 没找到就断言"代码里没有"——要写明搜了哪些关键词、哪些目录。

## 3. 计算脚本 `work/calc/`

所有派生数字（字节数、比例、行数、代码行数统计、曲线数据）都由脚本算出。

规范：

- 文件名 `EPxx_<主题>.py`，只用 Python 标准库，`python work/calc/EPxx_x.py` 直接运行。
- 开头注释写：算什么、输入从哪来（事实 ID 或源码路径）、哪些是假设（示意参数）。
- 输出用 `key = value` 一行一个，方便 tech-reviewer 对照屏幕。
- 示意计算（例如"假设输入 10,000 token"）必须在输出里打印"示意"字样，对应事实条目定为 E 级。

示例：

```python
"""EP03: 块状 KV 每输入 token 的字节数。
来源：F03-07 (main KV 288 B/压缩 token, cache_common.py)、F03-08 (index K 68 B)、
      F03-05 (KV 源层 2/8/14 为 2:1 压缩，20 为 1:1)。无假设参数。"""
MAIN, INDEX = 288, 68
layers = {2: 2, 8: 2, 14: 2, 20: 1}          # layer -> compress ratio
per_token = sum((MAIN + INDEX) / r for r in layers.values())
print(f"block_kv_bytes_per_token = {per_token:g}")            # 890
print(f"block_kv_MiB_per_128k = {per_token * 131072 / 2**20:g}")
```

## 4. 双人核验（★★★ 集）

EP03、EP04、EP07、EP12：

1. 两个 fact-checker 独立建账（互相看不到），分别写 `work/facts/_alt/EPxx_a.yaml`、`EPxx_b.yaml`。
2. 第三个任务 T-FACT-DIFF：逐条对比。两边一致的直接合并；一边有一边没有的，回源码确认后决定；两边矛盾的，必须给出源码原文定案，或标 `conflict` 进 `open_questions.md`。
3. 合并结果写 `work/facts/EPxx.yaml`，并在 `work/research/EPxx.md` 末尾记录分歧数量与处理结果。

## 5. 审校时的核对（tech-reviewer）

对脚本的每个镜头：

1. 旁白和屏幕字的每个技术断言，是否被镜头引用的事实**真正支撑**（不只是"ID 存在"）？
2. 措辞强度与等级是否匹配（B 级说成了"代码里"？E 级说得像定论？）
3. `scope` 是否正确（讲文档内容却标了 `oss`？）
4. 简化有没有越过"说错"的线？
5. 有没有把不同条件的数字放在一起比？
6. 数字是否与 `calc` 脚本输出一致？（重跑脚本）

对关键帧：屏幕上的数字、标签、代码路径与行号、角标颜色是否与账本一致。

## 6. 发现错误时

- 账本错了：fact-checker 改账本，在条目里加 `verified_by` 记录，showrunner 查哪些脚本引用了它（`grep -rn F07-09 work/scripts`），对应集回到 P4。
- 成片发布后才发现：在 `decisions.md` 记录，修脚本，只重做受影响的镜头（`tts.py --shots`、`render.py --shots`），重新合成。
