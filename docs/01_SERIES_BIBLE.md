# 01 系列圣经（SERIES BIBLE）

所有 Gemini 代理在动笔前读这一份。它规定"这个系列是什么样子"：讲什么主线、用什么案例串起来、每集长什么样、用什么口吻。

## 1. 核心论点

> DeepInfer 是 DeepSeek 为**一个模型**（DeepSeek-V4.1-Flash）、在**一种部署形态**（prefill/decode 分离、decode 宽专家并行、KV cache 外置长期保留）下、把**每个 token 的服务成本**压低而做的**专用推理引擎**。它几乎每个"奇怪"的设计，都能追到三个源头之一：
>
> 1. **模型长什么样**——40 层全部是 128 窗口的滑动窗口注意力；只有 4 层产生长期保留的块状 KV；后 20 层复用第 20 层投影出来的 KV（YOCO/CED 结构）；带 MTP 草稿头和置信度头。
> 2. **系统怎么部署**——prefill 用普通 8 卡机，decode 用 64–128 卡超节点；KV cache 存在独立存储集群里保留 3–7 天。
> 3. **生产要什么**——多厂商硬件（NVIDIA SM100 + 华为昇腾 950）、结果可复现、结构化输出、高吞吐和低延迟都要。
>
> 开源的只是其中的**引擎**，只做离线推理。专用换来了深度协同，代价是通用性和"开箱即用的在线服务"。

这段话是"导演的论点"。showrunner 在 P1 可以修正它，但修正必须基于事实账本。

**这段话里的每个数字在上屏前都要进事实账本**（`GLOBAL.yaml`），这里只是写作方向。

## 2. 三条主线

每一集都要在这三条线上找到自己的位置。

### 主线一：三个源头（为什么这样设计）

每个机制讲完，屏幕右侧出现"三源头"小图（模型 / 部署 / 生产），点亮它来自的那个源头。EP13 回收时，三源头图上挂满了各集的机制。

### 主线二：开源边界（代码里有 vs 文档里说）

每个镜头右上角有范围标签：`开源代码里有`（绿）、`仅文档描述 · 未开源`（琥珀）、`代码 + 文档`（蓝）、`通用概念`（灰）。EP02 第一次画出完整系统图并把开源部分高亮；EP11 整集讲琥珀色那一半。

### 主线三：和 vLLM、SGLang 的关系（专用换来了什么）

第 5–10 集每集末尾有一个 30–60 秒的"vLLM 和 SGLang 怎么做"小段，为 EP12 铺路。规则：只讲做法和取舍，不讲"谁更快"。

## 3. 贯穿案例：一个请求的一生

整个系列跟着同一个请求走。默认设定（P1 可以改）：

> **"第五轮"请求**：一个编程 agent 和模型已经聊了四轮，第五轮发来一个约 6 万 token 的输入（前四轮的上下文几乎全在里面），要求模型输出一个 JSON 格式的修改计划。

选它的理由：它同时触发几乎所有机制——长前缀命中（KV 存储、SWA 重放）、长 prefill（有界重放、分块）、decode（ZOS、DSpark、宽 EP）、结构化输出、协议解析（deepseek-recipe）。

> 注意：这是**虚构的示意请求**，不是 DeepSeek 公开的真实流量。用它时数字只能是示意值（标"示意"），或者是账本里有条件的真实数字。

### 站点地图

`dvlib.MiniMap` 实现了这张小地图，在片头卡、段落卡和站点切换时出现（默认大小，不缩成角落装饰；版式见 04 第 4 节），高亮当前站点：

| 站点 | 发生了什么 | 主要集 | 范围 |
| --- | --- | --- | --- |
| 入口 | 协议解析成 token（deepseek-recipe）、前缀匹配 | EP11、EP02 | 文档 + recipe 仓库 |
| 路由 | 选哪台 prefill、哪台 decode（负载均衡器） | EP11 | 仅文档 |
| Prefill | 命中前缀 → 补算 SWA → 处理新 token；后 20 层只算末尾 | EP03、EP06、EP07 | 开源代码 |
| KV 存储 | 块状 KV 与 SWA 状态写入/读出 3FS | EP06、EP11 | 文档为主，代码只有接口 |
| Decode | ZOS 调度、DSpark 投机、宽 EP + EPLB、结构化输出掩码 | EP05、EP08、EP09、EP10 | 开源代码 |
| 输出解析 | token 流解析回 API 格式 | EP11 | recipe 仓库 |

EP04 讲代码地图时，把这条路在**代码里**再走一遍（`LLM.generate()` → 引擎 → C++ 调度器 → worker → 模型 → 内核）。

## 4. 每集固定结构

不是死板模板，但每集都要有这些部分，顺序可以微调。

| 段落 | 时长 | 作用 |
| --- | --- | --- |
| 冷开场 | 30–60 秒 | 一个反直觉的事实或问题，直接进入。不要"大家好，这一集我们来讲……" |
| 片头卡 | 5 秒 | 集号 + 标题 + 小地图（当前站点高亮） |
| 本集问题 | 20–40 秒 | 一句话核心问题；本集在三条主线上的位置 |
| 正文：问题 → 思路 → 做法 → 代价 | 主体 | 每个机制都走这四步：不这么做会怎样（具体数字或场景）；核心想法（一张图）；DeepInfer 怎么做（代码在哪）；换来什么、付出什么 |
| 暂停题 | 每集 1–2 个 | "停一下：如果……会怎样？"屏幕给 5 秒，然后揭晓。给委托人自测用 |
| vLLM / SGLang 怎么做 | 30–60 秒 | 第 5–10 集必有 |
| 三句话 | 30 秒 | 本集"看完能说出"的三句话，逐条上屏 |
| 下集钩子 | 10–20 秒 | 留一个本集没解决的问题 |

## 5. 口吻与角色

- **讲解者**（旁白主声，Qwen 音色 `longanhuan_v3.1`）：一个懂行的工程师同事。冷静、具体、愿意承认"这里文档没说"。不煽情，不卖关子到让人烦。
- **提问者**（第二声，Qwen 音色 `longanlingxin_v3.1`，脚本里以 `Q：` 开头）：委托人的替身。只问真实的疑问——"为什么不直接……？""那代价是什么？""这和上一集说的……矛盾吗？"。每 3–4 个镜头最多出现一次，每次一句话。
- 两个声音的语气由配音提示词控制，规则见 `03_NARRATION_STYLE.md` 第 12 节。
- 不出现主持人形象，不用表情包、梗图、音效笑点。

## 6. 观众画像（就是委托人）

- 有软件工程背景，懂 Python，知道 Transformer、注意力、MoE 的基本概念。
- 听说过 vLLM，可能用过；没读过推理引擎源码。
- 想真正搞懂，愿意花几个晚上看完，不需要被哄，需要被带路。

默认观众**不知道**：PagedAttention、continuous batching、prefill/decode 分离、专家并行、投机解码、KV 量化的细节。EP01 负责打底，后面用到时回指（"EP01 讲过……"）。

## 7. 术语表（种子）

全系列统一用法。第一次出现时：中文名 + 英文 + 一句白话解释。最终版由 showrunner 维护在 `work/glossary.md`。

| 写法（字幕） | 读法（配音） | 一句话 | 首次出现 |
| --- | --- | --- | --- |
| prefill | prefill | 一次性处理整段输入，算出它的 KV | EP01 |
| decode | decode | 一步一步生成输出 token | EP01 |
| KV cache | K V cache | 注意力里每个 token 的 key 和 value，存下来给后面的 token 复用 | EP01 |
| 块状 KV | 块状 K V | V4.1 里按块分页存放、长期保留的 KV（只有 4 层产生） | EP03 |
| SWA | S W A | 滑动窗口注意力：每个 token 只看最近 128 个 token | EP03 |
| SWA 状态 | S W A 状态 | 每个序列一个固定槽位，存最近的 SWA KV | EP06 |
| YOCO / CED | Y O C O | 前 20 层算 KV，后 20 层复用的层结构；CED 是文档里的叫法 | EP03 |
| 有界重放 | 有界重放 | 只重算最后一小段 token 来近似重建 SWA KV | EP07 |
| ZOS | Z O S | 零开销异步调度：CPU 提前安排下一步，处理的是上一步的结果 | EP05 |
| 专家并行（EP） | E P | 把 MoE 的不同专家放到不同 GPU 上 | EP01 |
| 宽专家并行（Wide-EP） | 宽 E P | EP 规模到 64–128 卡 | EP08 |
| EPLB | E P L B | 专家负载均衡：复制热门专家，定期重排 | EP08 |
| MTP | M T P | 多 token 预测，用作投机解码的草稿来源 | EP03 |
| DSpark | D Spark | DeepSeek 的投机解码方案，按置信度决定验证几个草稿 token | EP09 |
| 批不变 | 批不变 | 结果不随同批其他请求变化 | EP10 |
| TTFT | 首 token 延迟 | 从请求到第一个输出 token 的时间 | EP01 |
| TPOT | 每 token 间隔 | decode 时相邻两个输出 token 的时间间隔 | EP01 |

规则：业界通用、没有好译名的词用英文（prefill、decode、token、kernel、batch），全系列不换说法。

## 8. 视觉主线（详见 `04_VISUAL_LANGUAGE.md`）

- 颜色有固定含义：橙 = prefill/输入，蓝 = decode/生成，绿 = 块状 KV，紫 = SWA，金 = 专家，红 = 代价/浪费。
- token 永远是小方块；GPU/机器永远是圆角框；时间永远从左到右。
- 每个数字卡下面必有一行灰色小字写条件。
