## EP01 推理引擎到底在忙什么（14 分钟）

- **核心问题**：从"跑一次模型"到"每天服务上百万亿 token"，中间隔着哪些问题？
- **看完能说出**：
  1. 推理分 prefill 和 decode 两段：prefill 一次算很多 token，主要受算力限制；decode 每步只为每个请求算一两个 token，主要受显存带宽限制。
  2. KV cache 是推理的核心资源：存多少、放哪里、能不能复用，决定成本。
  3. 引擎的工作是在吞吐、延迟、成本之间找平衡，手段是批处理、并行、缓存复用、投机解码、内核优化。
- **必须讲**：prefill/decode；KV cache；continuous batching；TTFT、TPOT、吞吐；MoE 与专家并行（为什么 token 要在卡之间来回发）；投机解码的基本想法。每个概念只讲到后面够用，并说"第 X 集会细讲"。
- **aha 候选**：decode 时 GPU 的大部分时间在"搬"（读权重、读 KV），而不是"算"。用一个示意计算（fact-checker 写 `calc/EP01_intensity.py`：每步读多少字节 vs 做多少 FLOP，参数标明是示意）说明为什么 batch 越大越划算。
- **不要讲**：Transformer 推导；推理引擎发展史。
- **素材**：R01、R13、R14（概念部分）。
- **暂停题**：decode 时把 batch 从 1 加到 64，每个 token 的成本为什么会大幅下降？

## EP02 DeepInfer 是什么，不是什么（12 分钟）

- **核心问题**：DeepSeek 到底开源了什么？没开源什么？
- **看完能说出**：
  1. 开源的是生产引擎的离线推理部分：只支持 V4.1-Flash，只支持 SM100 和昇腾 950。
  2. 完整服务还缺三样：KV cache 系统、VE/Prefill/Decode 分离部署、副本间负载均衡。仓库里留着这些功能的"插槽"。
  3. DeepSeek 的生产系统是 E/P/D 三段分离 + 独立 KV 存储；三个设计目标是多厂商硬件、普通机器拼部署、KV 保留 72 小时以上。
- **必须讲**：README 的定位原文；特性列表逐条一句话（写明第几集细讲）；"没包含"的三项；完整系统图并高亮开源部分（**全系列最重要的一张图**，EP11、EP13 回用）；官方规模数字（155 万亿 token/天、每 GPU 小时 38 美元，注明是 DeepSeek 自己说的、谷时定价口径）；deepseek-recipe 的定位。
- **aha 候选**：仓库里的"插槽"——`EngineType` 三态、一组空实现的虚函数、恒返回 `False` 的 `should_copy_state()`（R12 #1）。"大部分引擎功能已实现"指的是这些插槽和调度机制，不是跨机传输本身。
- **不要讲**："冲击 NVIDIA"之类的评论。
- **素材**：R01、R03、R12、R17。
- **暂停题**：如果你想用 DeepInfer 直接对外提供 API 服务，最少还要自己补哪几块？

## EP03 先认识它服务的模型（18 分钟）★★★

- **核心问题**：V4.1-Flash 的哪些结构特点，决定了 DeepInfer 长成现在这样？
- **看完能说出**：
  1. 40 层全部是 128 窗口的 SWA；只有 4 层（2、8、14、20）产生长期保留的块状 KV，摊到每个输入 token 约 890 字节。
  2. 前 20 层（encoder）对全序列算 KV；后 20 层（decoder）复用第 20 层投影出的 KV，自己只需要 SWA——这是 EP07 有界重放的前提。
  3. 模型自带 MTP 草稿层和置信度头，这是 EP09 投机解码的前提；还有占参数四分之一的 Engram 查表。
- **必须讲**：总参数与激活参数（以 HF `config.json` 推算为准，不用媒体数字）；`compress_ratios` 如何决定每层类型（0 = 纯 SWA，2 = SWA + 2:1 压缩，1 = SWA + 不压缩/共享）；MLA 在 V4.1 里实际是 64 头 query 对一条 512 维共享 latent（R02a #1）；890 B/token 的算式（`calc/EP03_kv_bytes.py`）；SWA 状态每序列固定约 2.8 MB、与长度无关（R02a #3）；Engram 是超大稀疏 n-gram 查表（R02b #3、R02c #1）；MTP 3 层 vs 每步猜 5 个是两个独立超参（R02c #2）；低精度格式（FP4 main KV、MXFP4 indexer K 与专家权重、MXFP8 SWA KV）；**"模型特点 → 引擎设计"对照表**（全系列的索引，后面每集回指）。
- **aha 候选**：
  - "40 层里只有 4 层的 KV 需要长期保留"——用 40 层竖排的动画，逐层点亮它产生什么。
  - "短上下文时，状态缓存反而比块状 KV 更贵"——两条曲线在约 3,277 token 处相交（R02a，E 级推算，需 `calc` 复核）。
- **不要讲**：训练方法、评测分数、和别的模型比智商。
- **注意**："encoder/decoder"是文档术语，代码里叫 `n_prefill_layer` 之前/之后、`yoco consumer`（R02b）。CED、YOCO、Engram、mHC、DFlash 这些名字的含义必须查清出处，查不清就说"代码里叫 X，公开资料没解释"。
- **素材**：R02a、R02b、R02c、R06、R07。
- **暂停题**：为什么说"后 20 层不需要逐 token 算块状 KV"是有界重放成立的前提？

## EP04 代码地图：一个请求在仓库里的一生（15 分钟）★★★

- **核心问题**：打开仓库从哪读起？一次 `LLM.generate()` 在代码里经过哪些地方？
- **看完能说出**：
  1. 分层：入口 → 引擎（Python 装配）→ **C++ 调度器** → worker → 模型执行 → 内核（TileLang 算子与 vendor 库）。调度器是 C++ 的，这是和 vLLM 最结构性的差别。
  2. 代码重心在算子层：`tilelang_ops/` 约占 `deepinfer/` Python 代码的一半，`cuda/` 与 `asc/` 两套镜像维护。
  3. 多卡不是张量并行：一个引擎进程只管 `cp_size` 张卡；DP 副本之间每步用一次 all-reduce 投票决定"这一步做 prefill 还是 decode"；driver 只广播方法名和少量参数。
- **必须讲**：目录职责与代码量（`calc/EP04_loc.py` 实测统计）；从 `examples/offline_inference.py` 开始的请求追踪（每一步给文件和函数）；进程模型与 SHM 消息队列；`Sequence`、`SamplingParams`、`InputMetadata`；CUDA Graph；NVIDIA/昇腾的切换点；带 "Derived from vLLM" 头的文件（只占约 12%，全在胶水层，R03 #3）。
- **aha 候选**：driver 到 worker 的 RPC 只广播方法名和布尔参数，不回传结果（R04 #2）。
- **不要讲**：逐文件流水账。目录表之后只走主路径。
- **素材**：R03、R04、R15、R18。
- **暂停题**：为什么 DP 组里没活干的 rank 也要跑一个"陪跑"步？（答案在 EP08 揭晓，这里埋伏笔）

## EP05 调度：让 GPU 一刻不停（13 分钟）

- **核心问题**：CPU 的调度工作怎样才能不拖慢 GPU？
- **看完能说出**：
  1. ZOS：GPU 跑第 N 步时，CPU 同时处理第 N−1 步的结果并准备第 N+1 步；GPU 不再等 CPU，代价是 CPU 永远晚一步。
  2. "晚一步"带来两个难题：下一步的输入 token 还不知道（由 GPU 内核从上一步的采样结果里直接取），账本要先乐观推进再回填。
  3. 异步只发生在连续的 decode 步之间；prefill 步仍是同步的，会让流水线排空一次。
- **必须讲**：同步时间线与 GPU 空泡；ZOS 时间线；`execute_model_step` 的执行顺序；`gather_input_ids_zos`（R05 #2）；乐观账本 `total_inflight_tokens`（R04 #3）；它不是 DeepInfer 发明的（文档说参考了 SGLang 和 NanoFlow）；文档里的 prefill 二次代价模型**不在**开源代码里（R05 #3）。
- **aha 候选**：CPU 根本不构造老请求的输入 token——它们在 GPU 上从上一轮采样结果里被"捡"出来。
- **vLLM / SGLang**：vLLM 的 async scheduling 已默认开启，用占位 token（R13 #2）；SGLang 的 overlap 调度器自 v0.4.0 默认开启（R14 #3）。
- **素材**：R04、R05、R13、R14。
- **暂停题**：如果第 N 步某个请求已经输出了结束符，而 CPU 已经把它排进了第 N+1 步，会发生什么？

## EP06 KV 与状态缓存：两种记忆，两种管法（15 分钟）

- **核心问题**：V4.1 有好几种 KV，DeepInfer 怎么在显存里管它们？
- **看完能说出**：
  1. 块状 KV 用分页块管理（长度随上下文增长）；SWA 状态每个序列一个固定槽位（`StateBlock`，大小与长度无关）。生命周期不同，管法就不同。
  2. 代码里有三个不同的"128"（块大小、落盘粒度、字节对齐），别混。
  3. 开源版**没有**自动前缀缓存：`BlockManager` 只有空闲链表和引用计数；命中逻辑在未开源的入口和存储里，文档给的命中上限是 L − 134。
- **必须讲**：`cache_engine.py` 结构；`StateBlock` 的"存储区 + 丢弃区"（文档 + 代码）；134 = 128 + 6（6 = 投机回退）；每序列落盘 20 层 × 134 × 528 B = 1,415,040 B；`fork_seq` 是唯一的前缀共享原语；KV 量化格式的字节数（`cache_common.py`）。
- **aha 候选**：三个"128"（R06 #1）。
- **vLLM / SGLang**：vLLM 哈希块前缀缓存；SGLang `UnifiedRadixCache` + HiCache 三层（R14 #2）。
- **素材**：R06、R07、R12、R13、R14。
- **暂停题**：为什么 decoder 那 20 层的 SWA 不需要落盘？

## EP07 SWA 有界重放：只重算最后一小段（18 分钟）★★★ 试点集

- **核心问题**：缓存命中时少了 SWA KV，或者 decoder 层需要 SWA KV，怎样才能不把整段上下文重算一遍？
- **看完能说出**：
  1. 精确重建 SWA KV 很贵（文档：decoder 要把最后 2,560 个 token 跑过 20 层）；有界重放只重算最后一小段，并把注意力截断在重放段内，得到**近似**的 SWA KV。
  2. 用在两处：encoder 侧的缓存命中补算；decoder 侧的 prefill——后 20 层只对末尾 KEEP_TOKENS 行做前向（README 给 V4.1 的设置是 140，代码要求 ≥ 128 + 6）。文档说这"几乎让 prefill 总计算量减半"。
  3. 它是近似：仓库里的等价性测试验证的是两种截断实现彼此一致，**不是**截断与不截断一致；精度影响官方只给了定性说法，并说在后训练里模拟了同样的重放。
- **必须讲**：SWA 的具体例子；感受野逐层扩大为什么让精确重建很贵；`max(s, i−127)` 的含义；两个使用场景；文档"128"与代码"≥134 / 140"的口径差别；省的是"行"不是"层"（R07 #1）；第 20 层仍要对全长做投影，所以不到 50%（R07 #13）；mask 与 compact 两种模式；`yoco_equiv.py` 验证的是什么、不验证什么（R07 #21）；"命中长度由谁决定"不在本仓库（R07 #17）。
- **aha 候选**：
  - 一万 token 的输入，后 20 层只算最后 140 行（"行·层"账本，`calc/EP07_rows.py`）。
  - "测试通过 ≠ 近似无损"。
- **不要讲**：没有证据的精度结论；"微秒级""暴力截断"这类说法（上一轮书稿的错误，见 `07_KNOWLEDGE_BASE.md`）。
- **vLLM / SGLang**：P2 核实 vLLM PR #58132 与 SGLang 方案的实际状态，只讲核实过的。
- **素材**：R07（主）、R02b、R06、R11、R13。
- **样板**：`docs/11_SAMPLE_EP07.md`、`examples/ep07_sample/`。
- **暂停题**：KEEP_TOKENS 如果设成 128，会出什么问题？

## EP08 并行：注意力用 DP，专家用宽 EP（16 分钟）

- **核心问题**：一个 MoE 大模型怎么拆到几十张卡上，还保持负载均衡？
- **看完能说出**：
  1. 注意力用数据并行，MoE 用专家并行，DP 数等于 EP 数；开源代码里没有张量并行。DP 组之间不对齐 batch 大小，只对齐"这一步做什么"，没活的 rank 跑陪跑步。
  2. 宽 EP 让每卡只放少量专家；但按 DeepInfer 公布的 sweep 数据，EP64 相比 EP8 的优势主要在**低并发时的交互性**，高并发时吞吐差距收敛到约 5%（R16 #2，注意这些数据的口径）。
  3. EPLB 用冗余专家复制热门专家，按统计定期重排；prefill 与 decode 参数不同。
- **必须讲**：DP-Attention + EP-MoE 数据流；MoE 一层的六段流水（R08 #2）；DeepEP 与 Mega MoE（scale-up 域内才用）；EPLB 两级贪心与参数（文档数字 + 代码 `policy.py`）；`symm_mem` 搬运权重；balanced CP 是什么、为什么文档说生产不用；为什么不用 TP（证据 + E 级推断分开讲）。
- **aha 候选**：每卡专家从 52 降到 7（MoE 权重读量理论上少 7.4 倍），吞吐却只多 5%–53%——瓶颈已经不在 HBM 带宽（R16 #2，E 级推断，必须讲清是推断）。
- **vLLM / SGLang**：Wide-EP + EPLB 两边都有；vLLM 的"6% 以内"说法放到 EP12 讲。
- **素材**：R08、R10、R12、R16。
- **暂停题**：为什么 decode 要用尽量大的 EP，而 prefill 要用尽量小的 EP？

## EP09 投机解码：DSpark 只验证值得验证的（15 分钟）

- **核心问题**：草稿一次猜 5 个 token，每个都验证划不划算？
- **看完能说出**：
  1. 草稿来自 MTP 层，DFlash 一次前向猜出整块 5 个 token（块内双向注意力），不是 5 次自回归。
  2. 置信度头预测每个草稿 token 被接受的概率；引擎按"预期接受 token 数 ÷ 估计步耗时"选每步验证多少，步耗时曲线来自启动时对各 CUDA graph 桶的实测。
  3. 按 DeepSeek 的数据：验证长度从 5 降到 3.2–4.4，接受长度基本不变，每卡约 60 并发时吞吐 +4–7%；并发 16 时反而 −1.5%——因为低并发时步耗时曲线几乎是平的，少验证省不出时间。
- **必须讲**：固定长度验证的浪费；DFlash 块并行草稿（R09 #2）；置信度 → 全 batch 全局分配（R02c #3）；吞吐曲线优化（R09 #1）；同步路径 C++、ZOS 路径 GPU 内核两份实现（R09 #3）；文档数据表（用自己的话解读，画并发—收益曲线）；开关 `DEEPINFER_ENABLE_MTP_VARLEN`。
- **aha 候选**：−1.5% 不是 bug，是曲线形状的必然。
- **vLLM / SGLang**：SGLang 有官方 DSpark 实现，用 host 侧 confidence planner + ragged verify（R14 #3）。
- **素材**：R09、R02c、R05、R14。
- **暂停题**：为什么开启确定性采样时必须关掉变长验证？（EP10 揭晓）

## EP10 内核、双硬件与"结果可信"（15 分钟）

- **核心问题**：DeepInfer 的性能底座是什么？怎么同时支持两种芯片？同样的输入为什么在引擎里不一定得到同样的输出？
- **看完能说出**：
  1. 5 个外部内核库 + 仓库自研的 TileLang 算子；双硬件差异被压到很薄的一层：同名包构建期二选一，TileLang 算子 `cuda/` 与 `asc/` 同名镜像。
  2. 批不变 = 把批维度从归约形状里拿掉：关 split-KV、关 split-K、采样器一行一个 CTA + 定点 CDF（R11 #1）。
  3. 确定性采样靠"随机数下标是绝对位置"；变长 MTP 会让一个请求的验证长度依赖同批其他请求，所以必须关掉（R11 #2）。
- **必须讲**：各内核库一句话定位；Mega MoE；开源 FlashMLA 比内部版少一个 SASS 优化（文档：解码内核慢 5–10%，端到端不超过 5%）；结构化输出 = 上游 xgrammar + 自研调度与搬运（R11 #3）；`eval/` 验证的是"引擎没把模型跑坏"。
- **aha 候选**：同一个请求，旁边换了一个"邻居"，输出就可能变——浮点加法顺序的动画。
- **素材**：R10、R11。
- **暂停题**：批不变推理要付出什么代价？

## EP11 没开源的那一半（13 分钟）

- **核心问题**：要把 DeepInfer 变成完整的在线服务还缺什么？DeepSeek 自己是怎么做的？
- **看完能说出**：
  1. 架构图上入口后面有三个路由负载均衡器（Prefill / Decode / VE），EPLB 在服务内部；命中长度必须在路由前算出，所以入口要先做前缀匹配（R12 #2）。
  2. KV 存在独立的 3FS 集群（约 100 PiB SSD，agent 流量保留 3 天、聊天 7 天），任何 prefill 机器都能命中任何前缀，不需要按前缀亲和路由。
  3. 弹性与容错靠冗余配额和请求级重路由；deepseek-recipe 负责协议与 token 之间的编解码。
- **必须讲**：整集琥珀色"仅文档描述"角标；Prefill 负载均衡分档与配额；两份官方文本对 `cost(q, c)` 中 `q` 的定义不一致（R12 #3）——这正是"文档口径要注明出处"的活例子；KV 存储分层；弹性规则；recipe 的设计（防特殊 token 注入、流式解析）。
- **aha 候选**：为什么 KV 放在独立存储集群反而更简单——路由不用管前缀在哪台机器上。
- **素材**：R12、R01、R18。
- **暂停题**：如果 KV 存在每台 prefill 机器本地，路由器要多做什么？

## EP12 和 vLLM、SGLang 的真实关系（18 分钟）★★★

- **核心问题**：同样能跑 V4.1-Flash，三者到底差在哪？
- **看完能说出**：
  1. 根本区别是定位：专用 vs 通用。DeepInfer 可以把模型结构写死进调度和缓存；vLLM/SGLang 要照顾几百个模型，必须抽象。
  2. 血统：骨架冻结在 vLLM v0.2.x 时期，个别基础设施后来同步；留下的是"壳"，调度、KV 布局、采样、元数据准备都换成了自己的（R15）。内核库三者共用，差别主要在调度、内存、通信与重叠。
  3. 网上的性能数字大多不能直接比：README 的 Pareto 图是"实测步频 × 假设 75% 接受率"的换算值（R16 #1）；vLLM 的"6% 以内"来自官方推文，是跨集群对公布数字，缺 GPU 数与拓扑（R13 #3）。
- **必须讲**：逐维度对比（调度、KV 与前缀缓存、并行、投机解码、结构化输出、确定性、P/D 分离、硬件）——每个维度先说三者怎么做，再说差别为什么存在；"口径八问"（R16 §5.3）做成一张可复用的检查卡；被删的、被裁剪的、被替换的通用能力分三类讲（R15 #3）；社区反应的信息量部分（R17：硬件移植是主线；单机实测与官方叙事差距大）。
- **aha 候选**：Pareto 图上每个点都乘了同一个假设系数。
- **不要讲**：没有条件的"谁快 X%"；只有表格没有解释。
- **素材**：R13、R14、R15、R16、R17。
- **暂停题**：拿到一个"A 比 B 快 30%"的说法，你要先问哪几个问题？
