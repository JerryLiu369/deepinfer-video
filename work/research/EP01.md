## 1. 最重要的 3–5 个发现

1. **两阶段物理瓶颈彻底割裂**：Prefill 处理整个输入，矩阵乘尺寸大，算术强度高达数千 FLOP/Byte，属于算力受限（Compute-bound）；而自回归 Decode 步单请求每步仅生成 1 个 Token，算术强度暴跌至 2.0 FLOP/Byte，GPU 99% 的时间在等待显存搬运（F01-01, F01-02, F01-10）。
2. **批处理的核心收益是“均摊权重搬运”**：Decode 阶段将 Batch Size 从 1 提升至 64 时，模型权重同样只需从显存读取一次，但能同时为 64 个 Token 进行计算，算术强度线性提升 64 倍（从 2.0 提升到 128.0 FLOP/Byte），计算核心利用率从 0.6% 跃升至 40.8%，且步进耗时几乎不变，从而让每个 Token 的成本急剧下降（F01-03）。
3. **KV Cache 是并发与上下文容量的硬约束**：虽然 KV Cache 避免了历史 Token 的重复计算，但其占用随序列长度与并发线性膨胀，是阻碍单机承载大规模长文本请求的关键显存瓶颈（F01-04）。
4. **连续批处理消除了静态气泡**：传统静态批处理受制于木桶效应，而连续批处理（Continuous Batching）在每一步动态注入新请求与移出结束请求，是现代推理引擎的通用调度基石（F01-05）。
5. **分布式通信与草稿验证扩展了优化边界**：MoE 专家并行将部分计算分发到不同卡上，带来了跨卡重排通信的代价（F01-07）；投机解码则通过草稿多猜、主模型单步并行验证，将原本低强度的自回归步骤转化为高强度的批量验证（F01-08）。

## 3. 观众最容易误解的地方

| 误解 | 真相 | 事实 ID |
| --- | --- | --- |
| 以为推理就是一次性前向传播跑一遍模型 | 推理分为两段截然不同的过程：Prefill 算整个 Prompt 一次性出第一个 Token，之后 Decode 是几十上百次反复单步循环 | F01-01 |
| 以为增大 Batch Size 会让生成变慢很多 | 在 Decode 带宽瓶颈阶段，增大 Batch 只利用了原本空转的核心，单步延迟（TPOT）增加极小，而吞吐量翻倍 | F01-03, F01-06 |
| 以为只要显存放得下模型权重就能跑无限长的上下文 | KV Cache 会随上下文长度和并发请求数线性膨胀，长文本服务中 KV Cache 显存消耗常超过模型权重本身 | F01-04 |

## 5. 可视化素材

- 时序步骤：
  1. Prefill 一次性灌入 Prompt（橙色 TokenRow），GPU 满负荷高算力运行，产出首 Token 与初始 KV。
  2. Decode 循环展开：每步加载权重（金色），单 Token 矩阵乘，写回 1 个 Token（蓝色），读取历史 KV Cache。
  3. Continuous Batching：展示包含 4 个请求的时间线，短请求完成后立即移出释放槽位，新请求无缝插入。
- 数据表（附 calc 脚本 `work/calc/EP01_intensity.py`）：
  - Batch=1: 32 GFLOP, 16 GB 访存, 算术强度 2.0 FLOP/B, 算力耗时 0.032 ms, 访存耗时 5.000 ms, 利用率 0.6%。
  - Batch=64: 2048 GFLOP, 16 GB 访存, 算术强度 128.0 FLOP/B, 算力耗时 2.048 ms, 访存耗时 5.018 ms, 利用率 40.8%。
  - Prefill 4096: 131.07 TFLOP, 16 GB 访存, 算术强度 8192.0 FLOP/B, 算力耗时 131.072 ms, 瓶颈为 Compute。
- 结构关系：
  - “吞吐 - TTFT - TPOT” 三角平衡图。
  - MoE 专家并行通信：GPU 0~3 跨卡 Dispatch 与 Combine 交换 Token。
