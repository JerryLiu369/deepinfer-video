## 1. 最重要的 5 个发现

1. **40 层里只有 4 层（2/8/14/20）产生块状 KV**；其余 36 层没有 compressor，按 `layer_kv_map` 复用最近的源层。摊到每个输入 token 正好 **890 B**（F03-06、F03-13，`calc/EP03_kv_bytes.py`）。
2. **40 层都有 128 窗口 SWA，但只有 layer 0–1 是纯 SWA**；2–19 是 SWA + C2 2:1，20–39 是 SWA + C1 1:1。CSA2 的 38 层里：4 Full、4 Reindex、**30 Reuse**（F03-07、F03-09）。
3. **CED 让 prefill 只跑 encoder 半区**：官方口径 decode 16B、prefill 8B 激活参数；但第 20 层仍对全长做 attn_norm 并写出 decoder 块状 KV，截断只发生在 query 侧（F03-21、F03-22、F03-35）。
4. **763.2B 总参数里 196.9B 是 Engram 查表**，每 token 每层只读 24 行 × 256 维；decode 实际激活约 16.42B（F03-19、F03-25、F03-27、F03-22）。
5. **state 槽是固定开销，且比大纲说的 2.8 MB 大**：40 个主干层 2,830,080 B，加上 3 个 DFlash 草稿层与 3 个 C2 压缩状态，整槽 3,128,928 B（2.98 MiB）（F03-16）。

## 6. 未解决问题

- **为什么 decoder 用 C1（不压缩）、encoder 用 C2（2:1）？** 查过 `compress.py` 注释、报告 §2.3/§4.2.1、部署问答；没有解释。口径：只说“官方只给了结构，没有解释取舍”，不要编“因为 decoder 更该省”。
- **报告说 decoder 各层用 layer-dependent 投影，开源权重只有第 20 层有 compressor**（F03-05 vs F03-06）。已查权重索引与 `layer_kv_map` 别名；无法确认报告是否描述另一个 checkpoint。口径：按代码讲“21–39 复用第 20 层投出的那一份 KV”；原因记 `open_questions.md` Q-003。
- **8B prefill 的官方推导**：报告只给数字；F03-22 的“只算前 20 层”是 E 级解释，短 prompt 下不成立。
- **552B 的精确构成**：按权重元数据减 Engram/MTP/视觉得 551.57B，与 552B 四舍五入一致；分项合计与 HF total 差 430,080 个参数（0.00006%），未逐张量归类。
- **变长验证的生产开关**：开源 `DEEPINFER_ENABLE_MTP_VARLEN = EnvVar.bool()` 默认 False；官方文档描述生产使用变长验证。生产如何开启/是否默认开启未知，EP09 再定。
- **1M 上下文的质量**：config 只说明容量上限，不等于 1M 质量已验证；实际受 KV 容量与调度限制。
- **mHC 的 “m” 与 YOCO 的字母展开**：公开文本只写 mHC / Single-Pass mHC / YOCO；代码注释只说 hc_mult 是 hyper-connection heads 数，没有给出 “mHC” 的展开。不要自行写 “multi-head” 或 “mixed”。
