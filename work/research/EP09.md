## 1. 最重要的 4 个发现

1. **草稿生成是块并行单步前向，非自回归串行前向（F09-02, F09-03）**：DFlash 通过 `[golden, noise×4]` 构造输入，块内 5 个草稿槽位共享一份 `kv_index`，在非因果双向注意力下仅用 1 次前向（3 个草稿层）算完整块；块内自回归依赖由轻量级 Markov 头串行修正补齐（F09-05）。
2. **变长验证核心是"步耗时随批量变化的实测曲线"（F09-11, F09-12, F09-13）**：目标函数是 `预期接受 token 数 / 估计步耗时`。步耗时曲线由启动期各 CUDA Graph 桶（默认按 8 等距）实测 5 次取截尾均值得出，并在运行期用在线残差中位数动态更新斜率。
3. **16 并发亏损（-1.5%）与 60 并发增益（+5.4%）的物理根因（F09-17, F09-18）**：低并发下步耗时由固定延迟（权重加载、启动开销）主导，裁减 9 个 token 最多只跨 1 个 8 等距桶，省不出时间，抵不过 2.4% 的接受长度损失；高并发下算力进入关键路径，裁减跨越 11 个桶，节省耗时远超接受损失。
4. **C++ 同步调度与 ZOS GPU 内核两套实现（F09-15, F09-16）**：同步路径在 CPU 上全表扫描并完成请求分配；ZOS 异步路径下 CPU 只定总预算 `total_q`，逐请求分配下沉至 GPU 端的 TileLang 内核现场完成（cumprod、argsort、remap scatter）。

## 2. aha 候选（最反直觉的点）

1. **"少验证 token 反而吞吐下降 1.5%"不是 bug，而是 Roofline 曲线形状与量化桶的必然结果**：直觉认为少算就能省时，但在 Memory-bound 和小批量的平坦区，验证槽位几乎是"免费"的，盲目裁减只会平白丢掉可能接受的 token。
2. **跨请求预算争夺：高置信度的尾巴 token 可以挤掉低置信度的龙头 token**：排序是全局扁平排序，而不是为每个请求固定分配阈值。
3. **被拒绝的草稿 KV 根本不需要显式清理**：草稿 KV 只活一个 step，下一轮前向直接在 SWA 环形缓冲原槽位覆写，回退完全零成本。

## 3. 观众最容易误解的地方

1. **误解：草稿猜 5 个 token 需要自回归循环调用 5 次小模型**。
   - **真相**：DFlash 采用块扩散思想，非因果双向注意力一次前向算完全部 5 个位置，串行前向次数与块长无关（F09-02, F09-03）。
2. **误解：变长验证只是在置信度低于某个阈值（如 0.5）时截断**。
   - **真相**：DeepInfer 完全没有固定置信度阈值。它把所有请求的所有候选槽位排成一列，结合启动实测的硬件耗时曲线，逐个试算全局吞吐 `cur_expected / time_ms` 找到极大值点（F09-13）。
3. **误解：开启投机解码后，输出结果会带有概率随机误差或精度损失**。
   - **真相**：采用严格 Leviathan/Chen 概率拒绝采样，拒绝时按残差分布重采样，数学上严格保证输出分布无损；工程上仅有 `DRAFT_PROB_PENALTY=5e-5` 防止空分布的极微小扰动（F09-07）。

## 4. 与大纲的出入与调整

- 大纲提到"每卡约 60 并发时吞吐 +4–7%"，代码与官方部署文档在 48、60、72 并发实测分别为 +3.6%、+5.4%、+6.7%，吻合该区间（F09-17）。
- 明确指出确定性采样与动态变长验证互斥（F09-19），作为与第 10 集衔接的关键伏笔。
