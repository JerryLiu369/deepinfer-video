# EP03 研究简报（a 版，独立建账）

## 0. 元信息
- 代码：`deepseek-ai/DeepInfer` @ `9bd9cf2`（2026-10-21）。模型：HF `DeepSeek-V4.1-Flash-1017` 的 `config.json`、`model.safetensors.index.json`、`model-0000x` 头部。
- 官方文档：HF `DeepSeek-V4.1-Flash` 仓库的 `DeepSeek_V41_Tech_Report.pdf`（2026-10-26 读取，可访问）；仓库内 `doc/inference_deployment_qa.md`。
- 账本 26 条：A 19（其中 2 条带 caveat）、B 3（其中 2 条带 caveat）、E 4。
- 计算脚本：`calc/EP03_kv_bytes.py`、`calc/EP03_state_crossover.py`、`calc/EP03_params.py`。
- 交叉核对：FP4 专家的打包元素 278,585,671,680 ×2 = 557,171,343,360，与 HF API 的 I8 计数逐位一致，据此确认 763.2B 是逻辑参数口径。

## 1. 最重要的 5 个发现
1. 40 层里只有 **4 层**（2/8/14/20）真的持有 KV compressor、产生块状 KV；其余 36 层没有 compressor 权重，21–39 层把 `ca_cache` 别名到第 20 层（F03-05）。
2. 只有 **8 层**有 indexer（2/8/14/20/24/28/32/36）；4 层 Full、4 层 Reindex、**32 层 Reuse**，后 32 层根本不跑 top-k 选择（F03-06）。
3. 890 B/token 是精确值，不是约数：3×(288+68)/2 + (288+68) = 890，与官方报告摘要逐字节吻合（F03-09，`calc/EP03_kv_bytes.py`）。
4. **prefill 每 token 激活 8B、decode 16B**：CED 下 prompt token 只走前 20 层，后半只处理末尾 KEEP 个位置（F03-20、F03-23）。
5. Engram 两张表 196.6B 参数（占总参数 25.8%），但每 token 每层只命中 24 行、约 6K 个值（F03-13）。

## 2. aha 候选
1. **“只有 4 层产 KV、只有 8 层算 top-k”** —— 反直觉：观众默认“每层都有自己的 KV 和注意力选择”。证据 A（F03-05、F03-06）。画法：40 层竖排，4 层亮块状 KV、8 层亮 indexer、其余 32 层画“复用箭头”指回最近的源层；配 `890 B` 的堆叠条。
2. **“一个体积数字反过来证明结构”** —— 890 的算式闭合；若把 24/28/32/36 误算成独立 index-K 副本会得到 1,162，与官方不符。证据 A/E（F03-09）。画法：两条堆叠条，890 vs 1,162，后者的 170 变 442。
3. **“prefill 比 decode 便宜一半”** —— 反直觉：输入侧通常被当作更贵。证据 B（F03-20）+ E 解释（F03-23）。画法：两根参数柱 8B/16B，下方 20/40 层示意。
4. （备选）“短上下文时状态缓存反而比块状 KV 贵” —— 3,277 token 交叉（连续口径）。E 级，须在旁白里说“这是按每序列内存的示意比较”（F03-12）。

## 3. 观众最容易误解的地方
- **“40 层每层一份 KV”** → 只有 4 层产块状 KV；40 层各有自己的 SWA（F03-05、F03-07）。
- **“2:1 压缩 = 两个 token 取平均 / 丢一个”** → 是按通道 softmax 加权求和（F03-07）。
- **“890 B/token 就是全部 KV”** → 不含 SWA；SWA 是每序列 2.78 MiB 的固定开销（F03-09、F03-11）。
- **“763B 参数每个 token 都要过矩阵乘”** → 196.6B 是查表，decode 只激活 16.4B（F03-13、F03-22）。
- **“3 层 MTP 就是每步猜 3 个”** → 3 是层数，5 是每步位置数，两个独立超参（F03-15）。
- **“552B 是媒体口径”** → 它是官方技术报告原话；与 763.2B 的差别是 Engram 查表与草稿/视觉（F03-20、F03-21）。

## 4. 与大纲的出入
1. **“总参数以 HF config.json 推算为准，不用媒体数字”** → 官方报告直接写 552B 主干 + 196B Engram、8B/16B 激活；HF 权重元数据是 763.2B。建议两个口径都上屏：**552B 主干 / 763.2B 含查表**，并说明 552 不是媒体数字（F03-20、F03-21）。
2. **“后 20 层只需要 SWA”** → 后 20 层不产生自己的块状 KV，但仍要读共享 KV、复用 top-k、并算本层 SWA。建议改成“后 20 层不再产生自己的块状 KV”（F03-05、F03-07）。
3. **“两条曲线在约 3,277 token 处相交”** → 连续口径 3,277.16；按 128-token block 粒度是 3,328。建议屏幕写“约 3.3k token”，并说明是 E 级示意（F03-12）。
4. **“MLA 512 维共享 latent”** → 对，但 512 内含 64 维 RoPE，内部 rank 是 448（F03-08）。
5. **大纲未讲“只有 8 层算 top-k、32 层复用”** → 这是本集最强的结构事实之一，建议加一个镜头（F03-06）。
6. **大纲的 aha“40 层只有 4 层 KV 需要保留”** → 成立，且可以再往下推一层：4 层里 3 层还是 2:1 压缩，所以摊到每 token 只有 890 B（F03-05、F03-09）。

## 5. 可视化素材
- **层表（40 行）**：层号 / compress_ratios / 模式（Full-Reindex-Reuse）/ 是否有 indexer / 块状 KV 源（F03-02、F03-05、F03-06、F03-07）。
- **890 堆叠条**：main 720 + index 170 = 890；每层再拆 288/68（F03-09）。
- **state 布局条**：stored 20×134×528 = 1,415,040 B / dropped 同量 / ca_state 86,016 B，合计 2,916,672 B（F03-11）。
- **参数饼图**：路由专家 543.6 / Engram 196.6 / MTP 14.4 / 注意力 5.1 / 共享专家 1.4 / 其他（F03-21、`calc/EP03_params.py`）。
- **交叉曲线**：890 B/token × L 与 2,916,672 B 的两条线，交点 3,277（F03-12）。
- **精度表**：主 KV 288 / index-K 68 / SWA 528，各配格式（F03-19）。

## 6. 未解决问题
1. **为什么 decoder 用不压缩的 C1、encoder 用 C2？** 查过 `compress.py` 注释、报告 §2.3/§4.2.1、部署问答；没有解释。建议口径：只讲“C1 让 decoder 少一条 gate/state 路径”，不说动机。
2. **报告说 decoder 有 layer-dependent 投影，权重里只有第 20 层一份 compressor**（F03-04 vs F03-05）。查过权重索引（21–39 无 `attn.compressor.*`）与 `cache_engine.py` 别名逻辑；无法确认报告是否描述别的 checkpoint。建议按代码口径讲，并在 caveat 里说明文档差异。
3. **8B prefill 的官方推导**：报告只给数字。我们的“只算前 20 层”是 E 级解释；短 prompt 下不成立。
4. **552B 是否含 embedding**：我的分项 551.5B 含 embed+head；报告没写口径。上屏只说 552B，不解释构成。
5. **工具问题**：`tools/lint_facts.py` 不支持 `_a` 文件名（stem 检查 + calc 路径），本账本用临时副本 `EP03.yaml` 校验通过。
6. **知识库待更新**：`docs/07` 陷阱 #9 说“552B 等媒体数字是 D 级，不用”，与官方报告冲突；建议改口径为“552B 主干是官方数字，763.2B 是含查表的权重总数”。
