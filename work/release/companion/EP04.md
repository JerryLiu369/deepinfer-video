# 观看手册 · EP04 代码地图：一个请求在仓库里的一生

> 一页纸速查。所有代码入口与数字均来自事实账本 `work/facts/EP04.yaml` 与固定 commit `9bd9cf2`。

## 三句话

1. **三层架构立面，算子占半壁江山，vLLM 派生仅占 12% 胶水层**：仓库四万七千行 Python 代码中，带 `Derived from vLLM` 头部声明的文件恰好只有 23 个（6,817 行，占 12.4%），全部集中在参数配置与进程外壳等胶水层；核心模型前向、全部底层算子与纯 C++ 调度器 100% 自研；算子层 `tilelang_ops/` 独占 23,331 行（49.5%），在英伟达（`cuda/`）与华为昇腾（`asc/`）成对镜像维护（F04-01, F04-02, F04-03, F04-04）。
2. **多卡告别 TP 转向 DP/CP/EP，单向共享内存广播驱动从属节点**：单引擎实例仅掌管 `cp_size` 张卡，主进程 Driver（卡 0）独占 C++ 调度与采样；多卡通信彻底移除张量并行（TP），仅保留长序列上下文并行（CP）、批次数据并行（DP）与专家并行（EP）；控制面 RPC 采用 10 块各 1 MiB 环形共享内存（`MessageQueue`）单向广播 `(method, kwargs)`，从属 Worker 执行后零返回值，消除双向同步延迟（F04-11, F04-12, F04-13, F04-21）。
3. **错步流水线与 DP 投票防死锁，空闲卡强行占位陪跑**：单步模型执行严格按照 `Forward(N) → Post-process(N-1) → Sample(N)` 错步重叠时序隐藏主机传输延迟；DP 副本之间每步调用 `_dp_allreduce` 全规约两轮投票统一步型为 prefill 或 decode，消除 EP 专家通信死锁；无请求分配的空闲卡必须运行单词元占位陪跑步（`_placeholder_seq_metadata`）保障全网拓扑对齐（F04-14, F04-15, F04-16, F04-17, F04-18）。

## 本集的"为什么"

| 机制 | 源头（模型 / 部署 / 生产） | 换来什么 | 付出什么 |
| --- | --- | --- | --- |
| 调度器 C++ 化下沉 | 系统工程与生产需求 | 调度全流程释放 Python GIL，多线程后台并发修改账本；对象池消除单步对象分配与 GC 抖动（F04-14） | 跨语言调试难度提升，元数据结构需维护 pybind11 自动生成桩（`engine.pyi`） |
| 彻底抛弃张量并行 (TP) | 模型结构与集群拓扑 | 消除 Transformer 每一层内部极其敏感的卡间 All-Reduce 高频同步，带宽聚焦于长序列 CP 与专家路由 EP（F04-12） | 单卡显存必须足以容纳层结构主干权重，无法做超大单体密集模型的层内切分 |
| 环形 SHM 单向 RPC | 部署架构与系统工程 | 10×1MB 环形队列无拷贝广播，从属 Worker 零返回值，完全消灭跨进程双向应答延迟（F04-13） | 采样与后处理逻辑必须全部由 Driver 独占承担，从属 Worker 沦为纯张量计算执行器 |
| DP 全规约步型投票 | 专家并行 (EP) 通信拓扑 | 强制全网 DP 副本统一步调（全员预填或全员解码），彻底杜绝跨卡 MoE All-to-All 交换死锁（F04-15） | 引入每步一次的 CPU/Gloo 集合通信开销；步型冲突时个别卡必须推迟自身预填意图 |
| 空闲 Rank 占位陪跑 | 专家并行 (EP) 通信铁律 | 维持多机多卡专家路由通信网拓扑绝对对称，防止缺失节点导致集体通信挂起（F04-16） | 空闲卡白白消耗微量前向算力与通信带宽计算无效填充张量（留待 EP08 展开） |
| C++ 只算 offset/len | 系统工程与计算剪枝 | 调度器在 CPU 上只计算两个整数界限，把展开庞大 index 张量的负担推迟到 GPU 前向并行完成（F04-19） | 要求底层 CUDA/NPU Kernel 具备动态基于 offset/len 自行解包展开的能力 |

## 本集没讲透、留给以后的问题

- **ZOS 错步重叠的微观实现与异常处理（EP05 调度：让 GPU 一刻不停）**：本集展示了 `Forward(N) → Post(N-1) → Sample(N)` 的四步宏观流水线；但在异步模式下，当第 N 步某个请求已经输出了结束符（EOS），而 CPU 早已把它预排进了第 N+1 步时，系统到底如何撤回？`gather_input_ids_zos` 是怎样在 GPU 上从上一轮采样结果中直接“捡出”词元的？
- **双重显存缓存池的物理切分（EP06 KV 与状态缓存：两种记忆，两种管法）**：本集提到了 C++ 序列账本的乐观推进与回填；但对于 890 B/token 的块状全局 KV 与每序列固定 134 槽位的 SWA 状态，`CacheEngine` 在显存中到底如何分配？为什么代码里会有三个不同的“128”？

<summary>自测题答案</summary>

1. **答**：实测带声明的文件恰好只有 23 个、合计 6,817 行代码，仅占一阶 Python 代码总量的 12.4%（全仓 4.7 万行 Python）。它们全部局限在参数解析（`arg_utils.py`, `config.py`）、进程外壳（`llm_engine.py`, `worker.py`）和数据容器（`sequence.py`, `sampling_params.py`）等胶水模块；核心模型前向（`v4_modules/`）、全部底层算子（`tilelang_ops/` 23,331 行，占 49.5%）以及 C++ 调度引擎核（`csrc/` 5,909 行）100% 自研，没有一行借用代码。（出处：S01, S04, S05 / F04-01, F04-03, F04-04）
2. **答**：不仅是为了速度。最关键的收益有两个：第一，在执行调度与状态转移期间，通过 `py::gil_scoped_release` 彻底释放 Python 全局解释器锁（GIL），使后台多线程与跨卡通信完全不被 GIL 阻塞；第二，利用 C++ 静态预分配对象池（`SequenceMetadataPool`, `RequestOutputPool`），彻底消除了每步调度在 Python 虚拟机中频繁分配上百个微小对象带来的垃圾回收（GC）开销与性能抖动。（出处：S03, S13 / F04-14, F04-22）
3. **答**：因为张量并行（TP）要求在 Transformer 的每一层内部切分矩阵，产生高频、延迟敏感的卡间 All-Reduce 集合通信，这在超长文本和多节点通信下是巨大的带宽瓶颈。DeepInfer 彻底放弃了 TP，单卡承载完整的网络层；跨卡仅保留切分超长序列的上下文并行（CP）、切分独立批次的数据并行（DP）以及实现 MoE 专家全网路由交换的专家并行（EP）。（出处：S11 / F04-12）
4. **答**：采用了 10 块各占 1 MiB 的共享内存环形队列（`MessageQueue`，满 1MB 安全退回本地 Unix socket）。主控 Driver 仅把方法名和参数字典压入队列，从属 Worker 循环拉取并执行本地方法，执行完毕后不回传任何数据结果（零返回值），彻底消除跨进程双向同步等待。采样计算（`Sampler`）仅在 Driver 所在主进程独占执行，从属 Worker 直接返回空采样结构，输出结果直接借用 C++ 静态池通过 uint64 内存指针句柄传递给外层。（出处：S12, S19 / F04-13, F04-21, F04-22）
5. **答**：因为在专家并行（EP）拓扑下，所有卡必须在每一步协同参与全互联（All-to-All）专家路由数据交换。如果空闲卡由于没有请求而休眠挂起，通信网络就会因为缺少该节点的参与而导致其余所有卡的集合通信陷入永久死锁。因此空闲卡必须运行单词元占位请求（`_placeholder_seq_metadata`）强行参与前向与通信，输出结果被完全丢弃，以极低的微量算力代价保障全网拓扑同步。（出处：S14, S15 / F04-15, F04-16）
