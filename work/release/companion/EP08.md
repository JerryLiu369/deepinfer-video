# 观看手册 · EP08 并行：注意力用 DP，专家用宽 EP

> 一页纸速查。所有代码入口与数字均来自事实账本 `work/facts/EP08.yaml` 与固定 commit `9bd9cf2`。

## 三句话

1. **彻底摒弃张量并行，注意力走 DP，专家走宽 EP**：DeepInfer 在配置中直接令 `model_parallel_size = context_parallel_size`，前向通路中不存在任何张量并行（TP）型 all-reduce；Attention 采用数据并行（DP），MoE 采用专家并行（EP），默认配置下 DP 数严格等于 EP 数，每一层只有全量复制的 `ReplicatedLinear` 与按专家切分的 `ParallelRoutedLinear`（F08-01, F08-02）。
2. **异步批大小与步型投票，占位请求对齐集合通信**：DP 组内各卡完全不对齐 Batch 大小，C++ 调度器在每步仅通过一次 `MIN all_reduce` 投票决定全组执行 Prompt 还是 Decode；无任务的空闲 Rank 自动运行 1-token placeholder 占位步陪跑，以严格匹配 DeepEP dispatch/combine 集合通信的拓扑要求（F08-03, F08-04, F08-15）。
3. **Wide-EP 买的是低并发交互性与显存摊销，而非高并发峰值吞吐**：从 EP8 扩展至 EP64，每卡路由专家数从 52 个降至 7 个，本地 MoE 权重访存理论削减 7.43 倍；但在高并发下全卡聚合批增大，系统瓶颈转移至通信时延与启动开销，官方实测吞吐提升收敛至仅 5.0%（256 并发），Wide-EP 的真实战略意义在于极低并发下的极速响应与单卡显存解脱（F08-08, F08-11, F08-12）。

## 自测题

1. DeepInfer 为什么在开源代码中彻底移除了张量并行（TP），生产中又是如何解决大模型显存放置的？
2. 在 Attention DP 下，各个 DP 卡上的 Batch 大小完全不同，它们是如何完成 MoE 专家并行的集合通信的？
3. MoE 层内的共享专家（Shared Expert）是如何完成归约的？为什么它不需要独立的 all-reduce 通信？
4. EPLB 专家负载均衡在同一 NVLink 域内是如何完成专家权重搬运的？为什么不需要走 P2P 消息网络？
5. 为什么从 EP8 增加到 EP64，本地专家权重访存减少了 7.4 倍，但在 256 高并发下吞吐仅仅提升了约 5%？

---

<details>
<summary>自测题答案</summary>

1. **答**：DeepInfer 面向的是 MoE 架构，参数分片的大头已经被专家并行（EP）承担；Transformer 内部的注意力层和共享专家权重在单卡 80GB 显存下完全放得下，若再引入 TP，每层都会增加极其敏感的层内 all-reduce 同步，反而拖累步频。因此代码中完全舍弃了 TP，`model_parallel_size` 直接等同于上下文并行（CP），参数切分由 EP 独立完成。（出处：S02 / F08-01, F08-02）
2. **答**：各 DP 卡之间绝不同步 Batch 大小，只同步“步型”。C++ 调度器在每步通过 `MIN all_reduce` 投票统一步调（全部做 Prompt 还是全部做 Decode）；没活干的空闲卡会自动执行一个包含 1 个假 token 的 placeholder 请求，以确保所有卡在每一步都执行相同次数的 DeepEP dispatch/combine 集合通信。（出处：S03 / F08-03, F08-04）
3. **答**：共享专家没有独立的 all-reduce 路径。在执行完 Grouped GEMM 后，共享专家在扣减通信 SM 的保护下与 combine 通信并行计算，其输出结果直接作为 `bias` 传入 DeepEP 的 `combine` 函数，在归约 routed 专家结果的同时融入同一个收尾 epilogue 中，从而省去了一次独立的跨卡归约。（出处：S04 / F08-05, F08-06）
4. **答**：在同一 NVLink 物理域内，EPLB 通过 `torch.distributed._symmetric_memory`（symm_mem）分配单层权重的对称缓冲，各卡经过两次 `barrier` 同步后，直接通过 CUDA IPC 共享内存从配对卡的镜像中 `copy_` 读入所需权重，是纯显存直读而不是发网络消息，极大降低了重排开销。（出处：S05 / F08-10）
5. **答**：因为在 256 高并发负载下，全卡聚合的 token 数量极其庞大，系统早已脱离了纯 HBM 显存带宽受限区，算力利用率大幅上升，此时跨 64 张卡的 All-to-All 集合通信时延与内核启动开销成为了主导瓶颈。Wide-EP 的真正价值在于低并发时的极速交互（并发 8 提升 53%）与显存容量解脱，而非高并发下的峰值吞吐倍增。（出处：S01, S06 / F08-12）

</details>
