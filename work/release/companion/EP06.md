# 观看手册 · EP06 KV 与状态缓存：两种记忆，两种管法

> 一页纸速查。所有代码入口与数字均来自事实账本 `work/facts/EP06.yaml` 与固定 commit `9bd9cf2`。

## 三句话

1. **变长分页与定长槽位双轨并立，应对截然相反的注意力生命周期**：在 DeepSeek-V4.1 的 40 层结构中，仅有 4 层（第 2、8、14、20 层）全局注意力产生需要跨全序列累积的块状 KV，由 `BlockManager` 按 128 token 为粒度从物理池按需分页追加；其余 36 层局部滑窗（SWA）只需保留最近 128 个位置，由 `StateManager` 为每个序列分配固定独占的 `StateBlock` 槽位，无论上下文是一千字还是十万字，显存地盘纹丝不动（F06-02, F06-07, F06-08）。
2. **源码中的三个“128”相互独立，物理块实为扁平单字节切片**：阅读 DeepInfer 源码最关键的认知突破是彻底解耦三个“128”——逻辑容器容量（`block_size = 128` token）、存储落盘调度步长（`KVSTORE_GRAIN = 128` token 时钟）与底层的硬件物理对齐（128 字节算子跨度）；在显存中，物理块并非跨层张量数组，而是一维连续的 `uint8` 扁平字节带，层内 32 字节硬件对齐，整块按最小公倍数 1152 字节严格对齐（F06-01, F06-02, F06-03, F06-04）。
3. **开源版零自动前缀复用，生产三层存储依托 3FS 与网关前置**：C++ `BlockManager` 纯粹是基于 FIFO 空闲链表与引用计数的整型槽位分配器，既无基数树（Radix Tree）也无块级哈希表，释放即归还队列并被新请求直接覆写；显存内唯一共享仅靠显式 `fork_seq`（pin 整表并在首步 Decode 写时复制末尾未满块）；生产环境的前缀匹配完全前置到接入网关，由专用 3FS 集群与宿主机内存承载跨机持久化与 1.35 MiB SWA 状态，引擎只保留极致纯粹的调度与执行（F06-06, F06-16, F06-17, F06-18, F06-19, F06-20）。

*解构说明*：彻底解耦代码中的三个“128”。左侧蓝色卡片为逻辑容器，代表每个分页块负责装载 128 个压缩前 token 的注意力数据；中间绿色卡片为调度步长，代表存储系统只在序列 token 计数跳跃到 128 整数倍的时钟边界处触发落盘；右侧紫色卡片为硬件物理对齐，代表底层 TileLang 访存算子要求物理块的内存步长跨度必须是 128 字节的整数倍（在 FP4 模式下整块精确对齐到 1152 字节）。三者分别对应数据容器、调度节奏与硬件访存，互相解耦，不可混为一谈。

3. 阅读源码时看到的三个“128”（`block_size`、`KVSTORE_GRAIN`、128 字节硬件对齐）各自代表什么含义？它们之间是否存在因果绑定关系？

<summary>自测题答案</summary>

1. **答**：因为两类注意力机制在模型中的生命周期截然不同。在 V4.1 的全部 40 层中，仅有 4 层（第 2、8、14、20 层）是全局注意力，必须跨越整个上下文保留完整的历史 KV，其内存随输入线性膨胀，因此必须使用变长分页块（`BlockManager`）按需动态索取以消除外部碎片；而其余 36 层全部是局部滑窗注意力（SWA），每个位置只需要查看最近 128 个历史 token，历史状态滚动覆写，因此采用固定大小的 `StateBlock`（`StateManager`）为每个序列预留定长槽位。生命周期的分化决定了管理机制必须双轨分立。（出处：S01, S03 / F06-02, F06-07, F06-08）
2. **答**：主 KV 压缩向量包含 512 个数值元素。在 FP4 模式下，每两个元素打包成 1 字节，数值数据占 $512 / 2 = 256$ 字节；微尺度缩放因子占 32 字节，两者相加精确等于 $256 + 32 = 288$ 字节。在显存排布中，底层算子要求硬件访存跨度满足 128 字节对齐，同时必须是单 token 字节数 288 的整数倍；求两者的最小公倍数：$\text{lcm}(128, 288) = \text{lcm}(2^7, 2^5 \times 9) = 2^7 \times 9 = 1152$ 字节。因此整块物理步长严格对齐到 1152 字节，以最大化 GPU 访存合流吞吐。（出处：S06, S07 / F06-03, F06-04）
3. **答**：三个“128”相互完全独立，纯属巧合与各层设计指标的数字重合：
   - ① **逻辑容器**：`block_size = 128`，代表每个分页块负责装载 128 个压缩前 token 的 KV 数据；
   - ② **调度步长**：`KVSTORE_GRAIN = 128`，代表存储子系统的时钟落盘粒度，仅在已生成 token 数量达到 128 的整数倍时触发落盘；
   - ③ **硬件物理**：128 字节硬件对齐，代表 GPU 底层张量核心访存事务（Memory Transaction）要求的最小内存对齐跨度。三者分别属于容器设计、调度策略与硬件限制，不存在任何逻辑绑定。（出处：S15 / F06-01, F06-03）
4. **答**：SWA 滚动环由 128 个基础滑窗大小加上 6 个最大回退预算（$5 + 1$）构成，总计 134。多出的 6 个位置承担两重使命：
   - 一是**容忍投机解码回退**：在多步推演（MTP/投机验证）中，若后续 5 个候选词被模型拒绝，写入指针需要向后倒退 5 步重新对齐，多出的槽位确保回退指针不会滑出有效缓冲区；
   - 二是**吸收异步落盘滞后**：存储系统的异步落盘存在微小的时钟抖动与边界延迟，多出的冗余位置确保在跨边界写入时，落盘中的历史数据不会被当场覆盖。（出处：S11 / F06-09）
5. **答**：开源版 DeepInfer 内部**完全没有**前缀树（Radix Tree）与块级哈希查找表。源码中的 `BlockManager` 仅包含 `_free_blocks`（FIFO 空闲链表）与 `ref_count`（整型引用计数向量），物理块释放后直接插回链表尾部，并在后续请求到来时被直接覆写，无任何常驻内容缓存。生产环境的前缀匹配完全被**前置到了接入网关（Gateway / Proxy）**；网关根据提示词哈希完成前缀匹配后，将匹配结果与持久化块 ID 作为外部参数直接注入给引擎插槽；引擎本身只负责无状态的极致计算与执行。（出处：S17, S19 / F06-06, F06-16, F06-18, F06-19）
