# 观看手册 · EP05 调度：让 GPU 一刻不停

> 一页纸速查。所有代码入口与数字均来自事实账本 `work/facts/EP05.yaml` 与固定 commit `9bd9cf2`。

## 三句话

1. **时空错位消灭 24.6% 显卡空泡，ZOS 仅管连续解码**：在传统的同步调度中，显卡跑完 4.0 毫秒前向后，必须挂起等待 CPU 执行 1.5 毫秒的后处理与调度，导致 24.6% 的周期空转；ZOS（零开销调度）让 CPU 永远晚一步，在 GPU 跑第 N 步模型前向时，CPU 并行处理第 N-1 步输出并调度准备第 N+1 步，彻底消灭主机调度开销；异步重叠仅在连续解码步生效，预填（Prefill）步仍为纯同步并当场排空流水线（F05-01, F05-02, F05-04, F05-05）。
2. **GPU 现场捡词打破因果倒置，remap 映射消除行序错位**：当 CPU 滞后一步无法预知下一步输入 Token 时，主机侧对存量请求写入 0 字节，底层由 GPU 上的 TileLang 内核 `gather_input_ids_zos` 直接从显存里的上一轮采样结果中就地切片组装；针对解码步每步按序列总长降序重排导致的行号动态变动，CPU 按全局序列 ID 构造 `remap` 映射数组，保障显卡内核精准对齐上下文数据（F05-06, F05-07）。
3. **EOS 确定性代价换压倒性吞吐，工业界共识殊途同归**：遇到结束符（EOS）的请求因 CPU 滞后不知情会在第 N+1 步多跑一次无用前向，在下一步后处理中被直接丢弃；以 500 token 序列为例，多跑 1 步仅浪费 0.2% 算力，却换来全流程消除四分之一空泡与超过 30% 的吞吐提升；该重叠流水线思想源自 NanoFlow 与 SGLang，并在 vLLM 中默认开启，已成为现代生产级推理引擎的行业统一标配（F05-08, F05-18, F05-19, F05-20, F05-21）。

*解构说明*：ZOS 双轨时间错位与零开销重叠时序。上方为 GPU 计算轨道，连续无缝执行第 N 步与第 N+1 步模型前向（Forward，绿色）；下方为 CPU 调度轨道，向右平移一格，将第 N-1 步后处理（Post-process，浅蓝色）以及第 N+1 步元数据准备与 GPU 前向并发重叠。CPU 的同步检查点后移至上上轮采样事件（`sample_end_evt(N-1)`），由于该事件在 GPU 命令流中早于 Forward(N) 发射，CPU 在检查时显卡早已完成计算，从而将原本 1.5 毫秒的 GPU 等待空泡彻底压缩抹平为 0 毫秒。

<summary>自测题答案</summary>

1. **答**：ZOS（Zero-Overhead Scheduling）的核心机制是通过时间维度的错位重叠，让 GPU 执行第 N 步模型计算的同时，CPU 并行处理第 N-1 步的后处理并调度准备第 N+1 步，从而彻底消除同步调度中高达 24.6% 的 GPU 空闲空泡。单步固定四阶段为：1. 发射当前步主模型前向 Forward(curr)；2. 利用显卡计算时间空隙，CPU 处理上一步输出 Post(prev)；3. 发射当前步采样 Sample(curr)；4. 将当前步后处理延后至下一步与新的前向重叠（解码步）或当场执行（预填步）。它不改变四个阶段的基本依赖顺序，仅将后处理交割推迟了一整步，通过流水线错步重叠吞掉了数据同步延迟。（出处：S04, S05 / F05-01, F05-03, F05-05）
2. **答**：DeepInfer 采取了“压根不让 CPU 准备存量输入”的下沉解法。对于上一轮已经在批次中的存量请求，CPU 主机侧在输入数组中连一个字节都不写（全部留空）。底层由 GPU 上的 TileLang 内核 `gather_input_ids_zos` 直接读取显存里的上一轮采样输出（`prev_sampled_token_ids`）与预测词（`prev_predict_token_ids`），在芯片内部就地切片重组成当前步的输入张量。数据流在显存内部闭环，完全跳过了主机总线传输。（出处：S07, S08 / F05-06）
3. **答**：因为调度器为了保证内核计算的规整性，在每一步都会把当前批次所有请求按照当前总序列长度从大到小重新降序排序。新词不断生成，请求的长度动态变化，导致请求在批次中的行号每一步都会上下换位。为了防止第 N 步第 0 行的数据被错误拼接到第 N+1 步第 3 行，CPU 必须在调度时根据请求的全局唯一序列 ID，快速计算出一份 `remap` 映射索引数组传给 GPU，TileLang 内核顺着这份映射表精准找回上一轮对应的采样输出。（出处：S09 / F05-07）
4. **答**：发生什么：因为 CPU 始终滞后一步，在调度第 N+1 步时该请求在主机侧的状态仍为运行中，因此它会被再次送进显卡，以 EOS 本身作为输入多跑一次无用的前向计算；在第 N+1 步后处理中检测到 `is_finished()`，直接丢弃该次输出并回收 MTP 槽位，最终在第 N+2 步将其移出活跃队列并释放显存块。为什么不当场中断：若要当场中断，CPU 必须阻塞等待第 N 步的采样结果，从而重新引入 25% 的显卡空泡。算力损失：以 500 token 生成为例，多跑 1 步仅浪费 0.2% 的前向算力，以千分之二的微弱代价换取消灭四分之一的空转等待，是吞吐最大化下的极优工程代偿。（出处：S10, S11 / F05-08, F05-21）
5. **答**：完全没有实现。在全部开源代码中检索，`compute_quota_limit` 和 `quota` 变量的命中数为零，代码中没有任何时间预算、二次方程拟合或基于时间的 all-reduce 求解。开源版的预填分块纯粹基于硬 Token 预算（`max_num_batched_tokens`）与多模态图片单元对齐。源码中唯一的二次项公式是 `FlopsEstimator`，它仅仅在步进结束且开启统计时，用来估算并在日志中打印利用率（MFU），从始至终不参与任何调度与分块决策。文档中的二次时间配额属于未开源的内部生产系统设计。（出处：S16 / F05-14）
