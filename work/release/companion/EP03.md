# 观看手册 · EP03 先认识它服务的模型

> 一页纸速查。所有代码入口与数字均来自事实账本 `work/facts/EP03.yaml` 与固定 commit `9bd9cf2`。

## 三句话

1. **总参与主干双口径，百倍稀疏查表与原生 MTP**：开源权重元数据逻辑总参数为 763.2B（对应 48 个分片约 510 GB 存储），扣除查表、草稿与视觉后为官方报告的 552B 主干参数；全 MoE 架构（384 选 6）使单步解码仅激活约 16.4B 参数（2.15%）；Engram 稀疏查表独占 196.9B 参数（25.8%）但每 token 仅查 24 行；原生 3 层 DFlash 草稿层一次前向前瞻 5 个位置并由置信度头动态分配验证预算（F03-19, F03-21, F03-22, F03-25, F03-27, F03-31, F03-34）。
2. **40 层全 SWA 骨架，仅 4 层产块状 KV 均摊 890 B/token**：全模型 40 层全部具备 128 窗口的局部滑动窗口注意力（SWA），对应每序列固定 134 槽位的状态池（整槽约 3.13 MB）；全网仅第 2、8、14、20 四层持有压缩器写入块状全局 KV，其余 36 层复用源层或为纯 SWA，通过 FP4 量化与 C2 压缩使块状 KV 精确均摊至 890 B/token（主 KV 720 B + index-K 170 B）（F03-06, F03-09, F03-12, F03-13, F03-15, F03-16）。
3. **CED 架构分水岭：第 20 层全长投影与后 20 层轻量复用**：前 20 层 encoder 处理全序列；第 20 层作为首个 decoder 既对全长序列做归一化并完成全长全局 KV 投影，又供后 20 层完全复用；第 21–39 层免除块状 KV 写入而只需局部 SWA，使预填充 query 截断至末尾 KEEP_TOKENS（≥134，推荐 140）行的有界重放成为可能（F03-04, F03-05, F03-35, F03-38）。

## 本集的"为什么"

| 机制 | 源头（模型 / 部署 / 生产） | 换来什么 | 付出什么 |
| --- | --- | --- | --- |
| 全 SWA 骨架（128 窗口） | 模型结构（局部注意力骨架）与生产需求 | 局部注意力计算与局部 KV 缓存与长度解耦，单序列状态槽大小固定（134 位置约 3.13 MB） | 单层内无法直接跨越 128 窗口建立注意力，长程语义必须依赖全局分支与跨层传递 |
| 块状 KV 均摊 890 B/token | 模型结构（仅 4 源层 + 2:1 压缩 + FP4 量化）与生产需求 | 全局 KV 显存占用压低至 890 B/token（主 KV 720 B + index-K 170 B），大幅突破长文本并发显存墙 | 36 层不产块状 KV 必须跨层复用，引入稀疏索引寻址与 FP4 量化精度近似 |
| 因果编码器-解码器（CED） | 模型结构（前 20 层 encoder + 后 20 层 decoder，受 YOCO 启发） | 后 20 层免除块状 KV 投影与写入，使 prefill 阶段 query 能够截断至末尾 KEEP_TOKENS（≥134）行（有界重放） | 第 20 层必须对全长序列执行全量归一化与 KV 投影，成为关键交接瓶颈；后 20 层局部状态依赖重放重建 |
| Engram 稀疏查表（196.9B） | 模型结构（条件记忆模块）与生产需求 | 引入超大参数量（占总参 25.8%）记忆长程先验，每 token 仅查 24 行（读 6,144 个浮点数），避开千亿参数密集 GEMM | 占用约 196.6 GB FP8 存储，需要跨 rank 切分与专用通信算子，打断了该层 mega_mhc 残差内核融合 |

## 自测题

1. 官方技术报告称 V4.1-Flash 有 552B 主干参数，而开源权重元数据给出的总逻辑参数为 763.2B，这两个数字之间近 2,100 亿的差额由哪些模块构成？为什么两者并不矛盾？
2. 全模型 40 层主干都配备了 128 窗口的滑动窗口注意力（SWA），为什么说只有 4 层产生长期保留的块状全局 KV？其余 36 层如何进行全局注意力计算？
3. 官方报告中给出的每个输入 token 占用 890 字节块状 KV 是如何精确算出来的？如果错误地把 4 个重索引层也算作独立 KV 副本，会得到什么结果？
4. 每序列固定的 SWA 状态槽（约 3.13 MB）与随长度线性增长的块状 KV（890 B/token）在显存占用上呈现出怎样的“反转”现象？两条曲线的理论交叉点在多少个 token？
5. 在因果编码器-解码器（CED）架构下，为什么后 20 层的 prefill query 行数能够被截断到末尾 KEEP_TOKENS（≥134，推荐 140）行？第 20 层在其中承担了什么不可替代的职责？

## 本集没讲透、留给以后的问题

- **请求如何在异构架构中穿梭？（EP04 追踪一个请求在代码里的一生）**：本集厘清了 40 层全 SWA、4 层块状 KV、196B 查表与 3 层 MTP 等模型物理蓝图；但当一个真实请求进入 DeepInfer 时，它到底从哪个 API 入口进入？调度器如何感知这些异构层？计算核心又是怎样在不同层类型之间流转调度的？
- **分层存储与双重显存如何落地管理？（EP06 显存布局与分层缓存）**：固定 3.13 MB 的 SWA 状态槽与线性增长的 890 B/token 块状 KV 存在截然不同的生命周期与碎片特征；引擎在物理显存中是如何对这两类缓存划分内存池的？前 20 层 SWA 持久化到本机 Host 内存与后 20 层 dropped 区随请求传输的机制在底层调度中如何实现？
- **交接层与有界重放的精度如何保障？（EP07 SWA 有界重放）**：第 20 层完成全长投影后，后 20 层在 prefill 时仅保留末尾 140 行前向计算，这种强制截断切断了更早历史的注意力依赖；虽然理论行数减少约 49.3%，但这种非数学等价的截断在实际部署中是如何依靠后训练模拟消除精度损失的？跨请求前缀命中时，未落盘的后 20 层 SWA 状态又如何以常数级代价补齐？

<summary>自测题答案</summary>

1. **答**：两者统计口径不同。763.2B 是开源权重 safetensors 索引中 48 个分片的全部逻辑参数总和；官方报告的 552B 仅统计主干网络（backbone），扣除了近两千亿的稀疏哈希查表（Engram 196.93B，含表和投影）、多词草稿层（MTP 14.23B）、视觉与 aligner（0.49B）以及其他辅助张量。两者并不矛盾，而是“总容量”与“主干参数”的双重口径。（出处：S03 / F03-19, F03-20, F03-21）
2. **答**：在开源权重索引中，仅第 2、8、14、20 四层持有 KV 压缩器（`compressor.*`）并实际分配与写入 `ca_cache`。其余 36 层中：第 0–1 层是纯 SWA，不具备全局注意力分支；第 3–7 层复用第 2 层、第 9–13 层复用第 8 层、第 15–19 层复用第 14 层、第 21–39 层复用第 20 层的公共缓存区。但全模型 40 层每一层仍独立维护各自 128 窗口的局部 SWA 状态。（出处：S12 / F03-06, F03-09）
3. **答**：主 KV 每个压缩 token 占用 288 B（FP4 E2M1 数据 + 每 16 通道 scale），微缩 index-K 占用 68 B（每 32 通道 scale），合计 356 B/压缩 token。第 2、8、14 层为 2:1 压缩，摊到每个输入 token 各为 $356 / 2 = 178\text{ B}$；第 20 层为 1:1 共享，单独贡献 356 B。求和正好为 $3 \times 178 + 356 = 890\text{ B}$（主 KV 720 B + index-K 170 B）。如果把第 24/28/32/36 四个 Reindex 层也算作独立 index-K 副本，就会错误算出 1,162 B/token。（出处：S14 / F03-12, F03-13）
4. **答**：呈现“短文本状态槽占大头，长文本块状 KV 占大头”的反转。SWA 状态槽物理环为 134 槽位（128 窗口 + 6 默认回退），每序列固定分配约 3.13 MB（只算主干 40 层为 2.83 MB），开销与序列长度解耦；而块状 KV 随长度按 890 B/token 增长。整槽连续交叉点为 $3,128,928 / 890 \approx 3,516\text{ token}$（按 128-token 块分配粒度为第 28 个 block，即 3,584 token）。上下文超过 3.5k token 后，块状 KV 的节省优势才正式主导显存。（出处：S17 / F03-15, F03-16, F03-18）
5. **答**：因为第 21–39 层彻底免除了计算和写入块状全局 KV 的职责，只读不写全局缓存；预填充阶段若只为后续自回归生成准备上下文，该半区只需保证局部 SWA 能看到末尾 128 窗口及回退余量即可。第 20 层作为首个 decoder 层，承担了唯一的全长全局交接职责：它必须使用全量输入做 `attn_norm`，并投影出贯穿全序列的全局 KV 存入缓存，供后续所有层跨层复用。（出处：S20 / F03-04, F03-05, F03-35, F03-38）
