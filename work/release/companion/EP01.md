# 观看手册 · EP01 推理引擎到底在忙什么

> 一页纸。所有代码入口与事实均来自 `work/facts/EP01.yaml` 与 `work/facts/GLOBAL.yaml`。

## 三句话

1. 大模型推理在物理本质上割裂为两个阶段：预填充（Prefill）受 GPU 算力限制，解码（Decode）受显存带宽限制。（F01-01, F01-10）
2. 键值缓存（KV Cache）是推理系统的核心内存资产与第一约束：它避免了历史重算，但显存占用随长度与并发线性膨胀。（F01-04）
3. 推理引擎的核心使命是在吞吐、延迟与成本之间做精密权衡，核心手段包括批处理、动态连续调度、专家并行与投机解码。（F01-03, F01-05, F01-06, F01-07, F01-08）

## 本集的"为什么"

| 机制 | 源头（模型 / 部署 / 生产） | 换来什么 | 付出什么 |
| --- | --- | --- | --- |
| 批处理（Batching 扩大至 64） | 生产需求 | 权重只加载一次，同时服务多路计算，算术强度提升 64 倍，单字成本骤降 | 增加排队等待，请求的首字与排队延迟略有上升 |
| 连续批处理（Continuous Batching） | 生产需求 | 迭代步级动态调度请求进出，彻底消除短请求等长请求的静态气泡 | 调度器必须在每一步维护动态请求状态与显存插槽映射 |
| 键值缓存（KV Cache） | 模型结构 | 保存历史注意力 Key/Value，避免自回归每步二次重算历史上下文 | 显存随序列长度与并发线性暴增，成为单机容量硬上限 |
| 专家并行（EP 跨卡通信） | 模型 + 部署 | 将超大 MoE 模型的不同专家分散到多张 GPU 上，突破单卡显存限制 | 每个 token 必须跨卡网络重排转发，引入全互联通信时延与负载不均 |
| 投机解码（Speculative Decoding） | 生产 + 模型 | 轻量草稿快速猜测多词，主模型单步并行核验，打破单字带宽枷锁 | 草稿猜错时存在回退与废弃验证算力浪费 |
| Prefill / Decode 分离部署 | 部署形态 | 算力受限与带宽受限节点物理隔离，化解资源锁争抢与抖动 | 引入跨机 KV Cache 传输网络，增加了系统部署复杂度 |

## 自测题

1. 为什么大模型推理在物理硬件上必须拆分成 Prefill 和 Decode 两个完全相反的阶段？
2. 在单请求解码（Batch=1）时，为什么上千 TFLOPS 的高端 GPU 核心大部分时间在闲置发呆？
3. 解码阶段把 Batch Size 从 1 加到 64，每个 Token 的成本为什么会大幅下降，而单步耗时几乎不变？
4. 为什么说 KV Cache 是自回归推理的核心资源，也是单机并发服务的第一道容量瓶颈？
5. 传统静态批处理有什么致命缺陷，现代推理引擎的连续批处理（Continuous Batching）是如何解决它的？

<details>
<summary>自测题答案</summary>

1. 因为 Prefill 一次性处理整段用户 Prompt，矩阵尺寸大，算术强度极高（可超 8,000 FLOP/Byte），属于典型的算力受限（Compute-bound）；而 Decode 每次只为每个请求生成一个词，矩阵乘退化为向量乘，算术强度极低（仅 ~2.0 FLOP/Byte），属于典型的显存带宽受限（Memory-bandwidth bound）。两者硬件资源瓶颈截然相反。（S04–S06 / F01-01, F01-10）
2. 因为每生成一个词，GPU 必须把数十 GB 的模型权重完整从显存加载一遍（如 16 GB FP8 权重在 3.2 TB/s 带宽下需 5.0 ms），而单词 32 GFLOP 浮点计算只需 0.032 ms。计算核心算完后 99% 的时间都在空转等待显存总线搬运权重。（S06, S07 / F01-02, F01-10）
3. 因为在显存带宽受限下，单步加载 16 GB 权重的 ~5.0 ms 耗时是固定开销。Batch=64 时，加载一次权重同时给 64 个词共用计算，算术强度提升 64 倍至 128 FLOP/Byte，计算耗时被访存耗时掩盖，总耗时依然约 5.0 ms，但产出了 64 倍的 Token，单 Token 的硬件与访存成本大幅均摊。（S08, S09 / F01-03）
4. KV Cache 缓存了历史所有 Token 的键值向量，避免了自回归每步重复计算历史注意力；但其显存占用随请求数与上下文长度成乘积线性膨胀（$O(B \times L)$），在长文本场景下其显存消耗远超模型权重本身，直接卡死了单机能同时支撑的请求上限。（S10 / F01-04）
5. 静态批处理强制所有请求同进同出，短请求早早结束后必须原地等待长请求，导致槽位闲置产生大量算力与显存气泡；连续批处理在每一个迭代步（Iteration-level）动态调度，请求完成立即释放槽位，新请求立刻无缝插入，彻底消除了等待气泡。（S11, S12 / F01-05）
