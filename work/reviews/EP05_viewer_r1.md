## 1. 读后复述：看完能说出的三句话

1. **时空错位与重叠时序**：ZOS 让 CPU 永远晚一步，在显卡运行当前步前向计算的同时，CPU 并发处理上一步输出并调度下一步，从而消灭了同步调度下 24.6% 的显卡空泡；异步重叠仅在连续解码步生效，预填步仍为纯同步并排空流水线。（对齐 S01–S06）
2. **GPU 现场捡词与乐观账本**：CPU 根本不为存量请求构造输入 Token，而是由 GPU 上的 TileLang 内核直接从上轮采样张量中捡出并按 remap 映射对齐；显存块通过 `total_inflight_tokens` 乐观预留，采样完成后按真实接受数事后回填。（对齐 S07–S09, S12–S13）
3. **确定性代价与工业界共识**：已结束的请求因 CPU 滞后会多跑一次无用前向，但这仅浪费 0.2% 算力却换来消除四分之一空泡的压倒性收益；重叠调度思想源自 NanoFlow 与 SGLang，并在 vLLM 中同样默认开启，已成为现代生产级推理引擎的行业标配。（对齐 S10–S11, S18–S19）

## 2. 核心自测题作答（5 题闭卷作答）

- **问题 1**：什么是 ZOS？它在单步执行（execute_model_step）中是如何安排工序的？
  - **回答**：ZOS（零开销调度）的核心是让 CPU 滞后一步来重叠计算。单步固定四阶段：1. 发射当前步主模型前向 Forward(curr)；2. 利用显卡计算矩阵的时间空隙，CPU 处理上一步输出 Post(prev)；3. 发射当前步采样 Sample(curr)；4. 将当前步后处理延后至下一步与新的前向重叠。

- **问题 2**：在 ZOS 下，CPU 准备下一步调度时连输入 Token 都还不知道，DeepInfer 是怎么解决这个因果冲突的？
  - **回答**：CPU 根本不为存量请求准备输入数据（主机侧写入 0 字节）。底层由 GPU 上的 TileLang 内核 `gather_input_ids_zos` 直接从显存里的上一轮采样输出和预测词中就地切片重组，数据流在显存内部闭合流转，跳过总线传输。

- **问题 3**：为什么解码批次的行号每一步都在变？系统如何防止索引错位？
  - **回答**：因为调度器每一步都会把当前批次所有请求按当前总序列长度从大到小重新排序。新词不断生成导致行号动态换位。CPU 必须根据请求全局 ID 计算出一份 `remap` 映射数组，GPU 内核顺着该映射表精准找回对应的上下文数据。

- **问题 4**：如果一个请求在第 N 步输出了结束符 EOS，在 ZOS 下会发生什么？算力浪费有多大？
  - **回答**：因为 CPU 滞后一步不知道它已结束，该请求在第 N+1 步会被再次排进显卡，多跑一次无用的前向计算；其输出在第 N+1 步后处理中被直接丢弃，显存块在第 N+2 步回收。以 500 token 生成为例，多跑 1 步仅浪费 0.2% 算力，相比消灭 24.6% 显卡空泡是极划算的工程代偿。

- **问题 5**：官方部署文档中声称的“prefill 二次代价模型与 compute_quota_limit 时间预算”，在开源代码中到底存不存在？
  - **回答**：完全不存在。在开源代码中检索该变量命中数为零。开源版预填分块只有纯硬 Token 计数预算和图片对齐；代码里的二次项只是 `FlopsEstimator`，仅在步进结束时用来计算并打印利用率日志，不参与任何调度决策。
