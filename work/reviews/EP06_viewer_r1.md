## 1. 观众复述的三句话

1. **两种记忆两种管法**：块状 KV 随上下文长度线性增长，用类似虚拟内存的分页块管理；而状态缓存只针对局部滑窗和压缩边界，每个请求独占一个固定大小的槽位（`StateBlock`），与总长度无关。
2. **代码里有三个“128”**：一个是分页管理的逻辑块容量（128 token）；一个是落盘持久化的时钟步长（128 token）；一个是底层硬件算子的显存物理对齐（128 字节），三者完全独立。
3. **开源版没有自动前缀缓存**：开源 C++ 代码里的 `BlockManager` 只是最简单的先进先出（FIFO）双链表加引用计数，没有任何哈希查找和前缀树；命中逻辑前置在接入网关，持久化在外部 3FS 集群，开源引擎只负责接收注入。

（核验：与剧集方案所承诺的“看完能说出的三句话”高度吻合！）

## 2. 闭卷自测题测试（5 题）

### Q1：为什么短文本时，状态缓存反而可能比块状 KV 更占显存？
- **观众作答**：因为块状 KV 是按需分页分配的，在输入只有几十个 token 时可能只分配一个几十 KB 的物理块；而状态缓存（StateBlock）在请求一进来时，就必须为当前序列划出一整块固定槽位（容纳 20 层的 SWA 环和压缩累加器），并且显存规划还会额外为解码副本预留双倍空间，因此短文本下定长状态开销远高于变长块。
- **评分**：正确（出处：S01, S03, S10, S16）

### Q2：在默认 FP4 模式下，单 token 的主 KV 为什么是 288 字节？
- **观众作答**：因为主 KV 压缩向量有 512 个数值元素，FP4 格式下两个元素占一字节，数据部分是 256 字节；再加上每 16 个元素共享一个微尺度缩放因子（共 32 字节），两者相加正好是 256 + 32 = 288 字节。
- **评分**：正确（出处：S06）

### Q3：为什么 SWA 滚动环的长度是 134，而不是刚刚好的滑窗大小 128？
- **观众作答**：因为 134 = 128 + 6。其中 128 是局部注意力的滑动窗口，而多出来的 6 个位置是最大回退预算（对应投机解码 5 步 draft 加 1）。它用来在投机解码被拒绝时允许指针向后回退，同时也能吸收落盘调度时的边界滞后。
- **评分**：正确（出处：S11）

### Q4：为什么说代码里的三个“128”绝不能混淆？
- **观众作答**：因为它们的物理本质和度量单位完全不同：① block_size=128 是逻辑容器装多少个 token；② KVSTORE_GRAIN=128 是系统在多大 token 步长下触发落盘；③ 128 字节是底层 GPU 张量核心与算子的硬件内存对齐跨度。把 token 个数与物理字节数混为一谈会导致整个显存账本算错。
- **评分**：正确（出处：S15）

### Q5：开源版 DeepInfer 如何实现多个请求共享同一个系统提示词（Prompt）？
- **观众作答**：开源版并没有像 vLLM 或 SGLang 那样自动识别相同前缀的机制；它必须由调用方显式调用 `fork_seq` 原语，通过 `pin` 操作增加整张块表的引用计数并克隆状态槽，在首次解码写入时触发写时复制（COW）复制末尾块。
- **评分**：正确（出处：S17, S18）
