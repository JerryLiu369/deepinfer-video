## 1. 读后复述：看完能说出的三句话

1. **仓库分层与代码重心**：DeepInfer 结构上分为 Python 编排、纯 C++ 调度器和底层算子库三层；带 vLLM 派生声明的文件只有 23 个，仅占 12% 的外围胶水，而近一半的代码是成对镜像维护的底层高性能算子，核心调度器被全盘用 C++ 重写并释放 GIL。（对齐 S03–S05）
2. **多卡拓扑与单向通信**：系统彻底放弃了张量并行（TP），跨卡只有数据并行、上下文并行和专家并行；一个引擎只管 CP 张卡，主控 Driver 向从属 Worker 发送的共享内存 RPC 只有方法名和参数，从属卡执行无返回值，采样完全由 Driver 独占。（对齐 S10–S13, S19）
3. **错步流水与集体防死锁**：单步执行严格采用“当前步前向、上步后处理、当前步采样”的错步重叠时序；数据并行副本每步必须全规约投票统一做预填还是解码，空闲卡哪怕没有请求也必须跑占位陪跑步，以防止专家并行全网通信死锁。（对齐 S14–S17）

## 2. 核心自测题作答（5 题闭卷作答）

- **问题 1**：DeepInfer 仓库中带 "Derived from vLLM" 头部的代码占多少？主要分布在哪里？
  - **回答**：仅占约 12.4%（23 个文件、6,817 行代码），全部集中在参数解析、进程管理和序列容器等外层胶水模块；核心计算模型、全部底层算子与 C++ 调度器没有一行借用代码。

- **问题 2**：为什么调度器要从 Python 下沉重写为 C++？仅仅是为了执行速度吗？
  - **回答**：不仅是为了速度，更关键的是为了在执行调度时彻底释放 Python 全局解释器锁（GIL），让后台通信与线程不受阻塞；同时采用对象池消除每步 Python 对象的创建与垃圾回收（GC）性能抖动。

- **问题 3**：DeepInfer 多卡推理为什么没有张量并行（TP）？跨卡通信包含哪些模式？
  - **回答**：因为系统摒弃了单卡内部切分矩阵的高频全归约开销，转而把带宽用于长文本与稀疏路由。跨卡仅包含上下文并行（CP，切分长序列）、数据并行（DP，切分批次）和专家并行（EP，跨卡路由全互联）。

- **问题 4**：为什么当某张 GPU 无请求可处理时，不能待机休眠，而必须执行“陪跑步”？
  - **回答**：因为在专家并行（EP）下，所有卡必须同步执行全互联（All-to-All）通信。如果空闲卡不参与，通信拓扑就无法对齐，整个集群将瞬间发生死锁。所以空闲卡必须构造单 token 占位请求强行参与前向。

- **问题 5**：ZOS 异步调度在单步执行函数里是如何排列工序的？为什么能掩盖等待开销？
  - **回答**：固定排列为：1. 发射当前步模型前向 Forward(N)；2. 利用显卡计算的时间空隙，处理上一步后处理 Post(N-1)；3. 发射当前步采样 Sample(N)；4. 异步模式将本步后处理推迟至下一步。通过错步重叠，彻底掩盖了主机与显卡之间的数据传输延迟。
