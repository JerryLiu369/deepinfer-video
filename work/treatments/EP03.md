- 对大纲的改动：
  1. **修正参数口径冲突**：大纲提出“以 HF `config.json` 推算为准，不用媒体数字”。事实账本核验表明：官方技术报告中明确给出了 552B backbone 参数与 196B Engram 参数（B 级），HF 权重元数据给出的总逻辑参数为 763.2B（B 级），decode 单步激活参数经算术推导约为 16.42B（E 级）。本集采用清晰的双口径并列说明，彻底理清“763.2B 包含 196.9B 查表与 MTP，552B 为主干参数，解码仅激活 16.4B”的客观事实，不作非此即彼的排斥（F03-19, F03-20, F03-21, F03-22）。
  2. **修正 SWA 状态槽容量**：大纲称“SWA 状态每序列固定约 2.8 MB”。核验代码发现，2.83 MB 仅指主干 40 层；整槽还包含 3 个 DFlash 草稿层的 SWA（212 KB）与 3 个 C2 层的压缩状态（86 KB），按 1,056 字节对齐后整槽为 3,128,928 字节（约 3.13 MB / 2.98 MiB）（F03-16）。方案明确标出“主干 2.8 MB，整槽 3.1 MB”。
  3. **修正显存交叉点数值**：整槽口径下，SWA 状态槽固定开销与 890 B/token 块状 KV 的连续交叉点在 3,516 token，按 128-token 块分配粒度为 28 块（3,584 token），而非大纲依据漏算草稿层的旧口径得出的 3,277 token（F03-18）。
  4. **理顺“4 层产 KV”与“20 层落盘”的分工**：明确产生块状 KV 的仅有 2、8、14、20 四个源层；而持久化到 3FS 存储集群的是前 20 层（0–19）的局部 SWA 状态（1.35 MiB），两者属于不同维度的记忆管理（F03-06, F03-16, F03-17）。
  5. **明确第 20 层的特殊地位**：第 20 层既是 decoder 的首层，又负责用全长投影写出 decoder 唯一的块状 KV，因此其全长投影计算无法被截断（F03-04, F03-35）。

## 1. 一句话梗概

全面拆解 DeepInfer 的单一服务对象 DeepSeek-V4.1-Flash：从 763B 总参数中 196B 稀疏查表的惊人配比，到 40 层全 SWA 骨架中仅 4 层产出块状 KV（均摊 890 B/token）的精简设计，揭示“模型架构特性倒逼引擎工程实现”的第一设计源头。

## 2. 核心问题

为什么 DeepInfer 几乎无法复用现有的通用推理架构？它所服务的 DeepSeek-V4.1-Flash 模型到底有哪些反直觉的异构设计，逼得引擎必须定制每一处内存布局、算子内核与调度流水线？

## 3. 看完能说出的三句话

1. 40 个主干层全部包含 128 窗口的滑动窗口注意力（SWA）；但只有 4 层（2、8、14、20）产生长期保留的块状 KV，通过 FP4 量化与 2:1 压缩，摊到每个输入 token 仅约 890 字节。（F03-06, F03-09, F03-12, F03-13）
2. 模型采用因果编码器-解码器（CED）结构：前 20 层（encoder）处理全序列；后 20 层（decoder）直接复用第 20 层投影出的 KV，自身只需要局部 SWA（第 20 层仍做全长投影），这是 EP07 有界重放得以成立的前提。（F03-04, F03-05, F03-35）
3. 模型原生支持极端稀疏与投机解码：763.2B 总参数中包含 196.9B Engram 稀疏查表（每 token 仅查 24 行），decode 仅激活 16.4B 参数；自带 3 层 MTP 原生草稿层与置信度头，为 EP09 投机解码奠定基础。（F03-19, F03-21, F03-25, F03-27, F03-31, F03-34）

## 6. 冷开场

**A（手法：反直觉结构 Hook）**——画面：40 层竖排的模型骨架逐层点亮。当镜头拉向右侧的显存分配池时，原本预期的 40 组块状 KV 缓存栏，竟然只有第 2、8、14、20 这 4 层在真正写入显存，其余 36 层全部显示“复用/空白”。

> 一个四十层的大模型，读进几万个 token 的输入。在传统推理引擎里，每一层都要把整段历史的键值缓存存下来。可在 DeepInfer 里，如果打开显存分配器，你会看到一个反常的景象：整整四十层模型，竟然只有区区四层会产生长期保留的块状 KV！剩下的三十六层到底在复用谁？为什么它敢这么省？

**B（手法：显存魔术 Hook）**——画面：左侧亮出令人窒息的“7630 亿参数、100 万 token 上下文”，右侧显存条迅速收缩，最终定格在单个 token 仅需 890 字节的微小方块。

> 总参数高达七千六百三十亿，支持一百万 token 的超长上下文。在常规认知里，这样的庞然大物只要几轮对话，KV 缓存就会撑爆整排高端 GPU。然而官方报告却给出了一个惊人的账本：每个输入 token 占用的全局 KV 显存，只有区区八百九十个字节！这究竟是怎样的显存魔术？

盲选结果：**选 A**（见 `work/reviews/EP03_hook.md`）。
理由：A 版直接从模型的层级结构切入，40 层竖排点亮与仅 4 层写入的视觉反差直击“认识模型”这一集的核心使命，自然牵引出层类型分类；B 版的 763B 总参数与 890 B/token 显存魔术则保留至后文的 Aha 账本与显存分析环节作为核心武器展开。

## 7. aha 时刻

- **观众“原来如此”的那一刻**：
  1. **显存反转 Aha**：在短上下文时，每序列固定大小的 SWA 状态槽（约 3.13 MB）竟然比随长度增长的块状 KV（890 B/token）更耗显存！两条曲线在约 3,516 个 token 处相交——只有当上下文突破 3.5k token 后，块状 KV 的显存占用才正式反超状态槽（F03-18）。
  2. **严密自洽 Aha**：官方报告中看似惊人的“890 bytes per token”不是粗略估计，而是由 3 个 C2 压缩层各贡献 178 字节、加上第 20 层贡献的 356 字节，严格推导出来的数学结果（3×178 + 356 = 890 B）（F03-13）！
- **画面怎么实现**：
  1. 双轴坐标系动画：横轴为输入上下文长度（0 到 10,000 token），纵轴为显存占用（MB）。一条是平直的紫色水平线（每序列固定的 SWA 状态槽 3.13 MB），另一条是从原点斜向拉升的绿色直线（890 B × L 块状 KV）。两条线在 3,516 token 处交汇发光，下方标注“短文本时状态槽更占显存，长文本时块状 KV 均摊优势显现”。
  2. 堆叠条拼接动画：720 B（主 KV）与 170 B（index-K）无缝拼接成 890 B，下方对比反例“若 8 个 indexer 各存一份则是 1,162 B”，展示架构设计的精密收敛。
- **紧接着用什么防止误解**：
  1. 立刻说明：890 B/token 是“理论连续均摊”，实际显存分配按 128-token 块（每块 113,920 字节）整块划拨，存在内存对齐与块内碎片（F03-14）。
  2. 严肃澄清：“只有 4 层产块状 KV”绝不等于“其余 36 层没有 KV 计算”——每层都保有独立的局部 128 窗口 SWA，第 24、28、32、36 层还会重新计算独立的 top-k 索引（F03-06, F03-07）。

## 9. 暂停题

- **题目**：为什么说“后 20 层不需要逐 token 算块状 KV”是有界重放成立的前提？
- **答案**：
  因为在 CED（因果编码器-解码器）结构中，后 20 层（decoder）所需的所有全局块状 KV，已经在第 20 层通过全长注意力规范化和共享投影一次性全部生成并保存在 `ca_cache` 中（F03-04, F03-35）。后 20 层的每个 token 只需要查询这份共享的块状 KV 和自己本层局部 128 窗口的 SWA。
  如果后 20 层像传统 Transformer 一样，每一层都必须为历史 token 计算并保存属于本层的全局 KV，那么即使当前输入 token 的 query 侧想做截断，也必须将整段历史 prompt 逐层前向推进以产生每一层的 KV。正是因为后 20 层彻底免除了生成全局 KV 的负担，引擎才敢在 Prefill 阶段将后 20 层的计算完全截断在最后 140 行，使有界重放的行级截断能够真正成立（F03-05, F03-35, G-06）。
