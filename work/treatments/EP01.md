## 1. 一句话梗概

从大模型单次前向推理到每天服务百万亿 Token，剖析 Prefill 算力受限与 Decode 显存带宽受限的两阶段物理瓶颈，揭开推理引擎在批处理、缓存、并行与投机解码中寻找吞吐与延迟平衡的底层逻辑。

## 2. 核心问题

从本地跑一次模型，到云端每天稳定服务上百万亿 Token，中间到底横亘着哪些不可逾越的物理限制与工程挑战？

## 3. 看完能说出的三句话

1. 推理分为两段截然不同的物理过程：Prefill 一次处理整段 Prompt，受 GPU 算力限制；Decode 每次仅生成少量 Token，受显存带宽限制。（F01-01, F01-10）
2. KV Cache 是推理系统的核心内存资产与第一约束：它消除了历史 Token 的重复计算，但其容量随并发与上下文长度线性膨胀，决定了单机服务容量上限。（F01-04）
3. 推理引擎的核心使命是在吞吐、延迟与成本之间做精密权衡，核心工程手段包括连续批处理、专家并行、缓存复用与投机解码。（F01-03, F01-05, F01-06, F01-07, F01-08）

## 4. 站点与三源头

- 站点（MiniMap 高亮）：第 1 站（通用引擎机制与物理瓶颈基座）
- 三源头（模型 / 部署 / 生产）：
  - 模型：自回归机制与注意力 KV 依赖（决定了 Decode 循环与 KV Cache 膨胀）
  - 生产：低成本与高吞吐需求（推动了连续批处理与算术强度优化）
  - 部署：Prefill 与 Decode 物理冲突（催生了 P/D 分离架构演进）

## 6. 冷开场

**A（手法：反直觉悬念 Hook）**——画面：高端 GPU 芯片微距特写，计算核心全部呈现灰色空转，显存总线数据流极度拥挤红闪。

> 你买了一张昂贵的高端 GPU，上面有上千 TFLOPS 的恐怖浮点算力。但在生成文字时，它超过百分之九十九的时间都在空转发呆。很多人以为大模型推理是疯狂的矩阵运算；其实在解码单字时，它是一场被显存带宽死死卡住的漫长搬运。

**B（手法：规模冲突 Hook）**——画面：左侧单用户笔记本优雅输出文字，右侧数据中心服务器机柜指示灯疯狂闪烁，每天 155 万亿 Token 数据流压垮系统。

> 在本地电脑上跑一次大模型，感觉轻而易举。但如果要把这个动作放大到每天服务一百五十五万亿个 Token，系统就会撞上一堵坚硬的物理高墙。为什么单人可用的推理代码，一旦面对海量并发就会立刻崩溃？

盲选结果：**选 A**（见 `work/reviews/EP01_hook.md`）。
理由：直接击中 GPU 算力利用率极度低下的反直觉本质（“99% 时间发呆”），极具冲击力与好奇心牵引，直奔主题核心。将 B 中的规模数字融入后文生产挑战中。

## 7. aha 时刻

- **观众"原来如此"的那一刻**：Decode 阶段 GPU 的大部分时间在“搬”而不是在“算”；增大 Batch Size 并不是让算力多等 64 倍时间，而是在同一次 16 GB 权重搬运的间隙里，顺手帮 64 个 Token 完成计算！
- **画面怎么实现**：
  1. 搬运与算力时间轴展开：Batch=1 时，显存带宽搬运 16 GB 耗时 5.0 ms，而算力耗时仅 0.032 ms，计算核心空转 99.4%。
  2. 天平倾斜：左边是 16 GB 沉重的权重搬运，右边是轻飘飘的 32 GFLOP 计算。
  3. 批处理展开：当 Batch=64，权重搬运时间依然是 5.0 ms，算力耗时提升至 2.05 ms，但依然完全被 5.0 ms 的访存时间掩盖，计算利用率飙升至 40.8%，单个 Token 的成本骤降 64 倍！
- **紧接着用什么防止误解**：立刻补充“天下没有免费的午餐”——并发增加会带来 KV Cache 的线性暴增和排队延迟，指出推理引擎必须在显存与吞吐间精密取舍。

## 9. 暂停题

- 题目：在 Decode 阶段，把 Batch Size 从 1 扩大到 64，每个 Token 的生成耗时并没有增加几十倍，单 Token 的硬件成本却大幅下降，为什么？
- 答案：因为单请求 Decode 受限于显存带宽，GPU 大部分时间在等待模型权重从显存加载到核心。当 Batch=64 时，单步内 16 GB 的模型权重依然只加载一次，却能同时为 64 个 Token 进行矩阵乘计算，使算术强度从 2.0 FLOP/Byte 提升 64 倍到 128.0 FLOP/Byte，计算核心空转被填满，因此单步总耗时增加极小，而吞吐量成倍提升，摊薄了每个 Token 的显存搬运与硬件成本。（F01-02, F01-03）
