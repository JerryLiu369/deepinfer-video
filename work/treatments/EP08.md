# EP08 剧集方案：并行：注意力用 DP，专家用宽 EP

## 1. 一句话梗概

DeepInfer 在 64 卡集群上彻底摒弃张量并行，依靠注意力数据并行与专家并行解耦、C++ 步型投票对齐通信、NVLink 域内 Mega MoE 融合、EPLB 两级贪心装箱与 symm_mem 显存直读，用集合通信复杂度换取单卡极低专家访存，奠定超低交互延迟的并发底座。

## 2. 核心问题

当超大规模 MoE 模型部署到几十张 GPU 时，如何在没有任何张量并行（TP）的前提下，实现注意力与专家的并行解耦、规避长尾负载倾斜，并看清 Wide-EP 在物理层面的真实得失？

## 3. 看完能说出的三句话

1. DeepInfer 开源配置里没有张量并行（TP），Attention 走数据并行（DP），MoE 走专家并行（EP），两者进程组正交解耦；DP 组间不同步批大小，只通过 C++ 调度器进行 MIN 投票同步步型，没活的 rank 执行 1-token 占位步陪跑以对齐 EP 集合通信。（F08-01, F08-03, F08-04）
2. MoE 层具备六段前向流水线，共享专家扣减通信 SM 算力与通信重叠，并将输出作为偏置直接融入 combine 归约 epilogue；在 NVLink 物理域内更进一步通过 Mega MoE 将 dispatch、GEMM 与 combine 单核融合。（F08-05, F08-06, F08-07）
3. Wide-EP 从 EP8 提升到 EP64 将单卡专家权重访存削减 7.43 倍，但高并发下吞吐提升收敛至仅 5%，其本质是以通信换带宽换取低并发交互响应；负载倾斜依靠 EPLB 逐层两级贪心算法动态复制热点专家并在 NVLink 域内通过 symm_mem 共享显存直读。（F08-09, F08-10, F08-12）

## 4. 站点与三源头

- 站点（MiniMap 高亮）：Decode（解码计算阶段，重点展示专家路由与跨卡数据交换）。
- 三源头：
  - 模型源头：MLA 压缩注意力低维潜变量投影，使得 TP 切分通信比恶化，天然适配 DP-Attention + EP-MoE 解耦。
  - 部署源头：NVLink 物理域内具备高带宽共享显存直读（symm_mem）与单核融合能力（Mega MoE）。
  - 生产源头：在线服务极度渴求低并发交互首字与每字延迟，Wide-EP 核心服务于交互响应而非峰值吞吐堆叠。

## 6. 冷开场

**A（手法：数据反差）**——画面：左侧 EP8 吞吐扫描曲线，右侧 EP64 扫描曲线，大号数字天平对比 7.4 倍访存削减与 5% 吞吐提升。

> 如果你手握 64 张高端加速卡，让每张卡只负责极少数专家，单卡每次读取的权重理论上可以削减 7 倍以上。在官方基准扫描中，极低并发下每字交互速度确实暴涨；可一旦并发攀升到 256，宽 EP 的吞吐增益却迅速收敛到仅仅 5%。这多出来的数十倍通信代价，到底买到了什么？

**B（手法：架构设问）**——画面：展示单机 8 卡扩展到 64 卡全互联矩阵，token 跨卡飞散导致带宽报警。

> 传统大模型推理几乎离不开张量并行，每一层都在频繁做全规约通信。但在 DeepInfer 的开源配置里，张量并行被彻底抹去。当 64 张卡同时运转，注意力各算各的批次，专家跨卡频繁交换，系统如何保证通信不会瞬间死锁？

盲选结果：选 **版本 A**。数据反差极其鲜明，直击 Wide-EP 的核心物理悖论，更具科技科普的思辨张力。版本 B 中关于“张量并行被彻底抹去”的精辟阐述移至 S02 深入展开。

## 7. aha 时刻

- **观众"原来如此"的那一刻**：
  从 EP8 到 EP64，单卡专家数从 52 个暴降到 7 个，权重访存足足减少了 7.43 倍！然而在高并发下，64 张卡的聚合批次急剧膨胀，系统早已脱离了纯 HBM 带宽瓶颈，延迟主导权全面转移到了 64 卡跨机 All-to-All 集合通信与核函数发射开销。Wide-EP 根本不是为了拔高高并发吞吐，而是为了在低并发时实现极速人机交互与大显存摊销！
- **画面怎么实现**：
  S19 展现动态天平：左侧“HBM 访存节省”在低并发时沉甸甸下压，右侧“集合通信开销”在高并发时剧烈飙升，吞吐曲线两条线在 256 并发处完美粘合，屏幕弹出 5% 的红色收敛标注。
- **紧接着用什么防止误解**：
  S19 紧接着给出官方 Pareto 曲线的背景条件：固定 nextn=3、假设 75% 接受率折算系数 3.25，明确说明这是特定硬件与特定假设下的容量推算，并非所有场景的绝对定论。

## 9. 暂停题

1. **暂停题 1**：在 DP-Attention 组内，如果有几张卡当前批次没有任何请求，为什么它们不能直接闲置休眠，而必须执行一个 1-token 的假请求？
   - **答案**：因为下游 MoE 层的 DeepEP dispatch 和 combine 属于集合通信（Collective Communication），所有参与 rank 必须同时、同频进入对应的通信核函数。若空闲 rank 退出或休眠，正在计算的 rank 将在集合通信处永久阻塞挂死。
2. **暂停题 2**：从 EP8 扩展到 EP64，单卡本地专家权重访存量削减了 7.4 倍，为什么在 256 高并发下全系统吞吐仅提升了 5%？
   - **答案**：在极高并发下，全卡聚合的 token 批次已经非常大，计算与访存的算术强度显著提高，系统瓶颈不再由 HBM 权重读取时间主导，而是全面转移到了 64 张卡跨节点变长 All-to-All 集合通信开销与核函数发射延迟上。
